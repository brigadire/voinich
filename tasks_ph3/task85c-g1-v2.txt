Task85c — G1-v2 Executable Scientific Contract Resolution


PURPOSE

Resolve the scientific-contract ambiguities discovered by
Task86C-v2-scientific-impl and transform the frozen Task85b
methodological design into a uniquely implementable, machine-checkable
G1-v2 scientific contract.

Task85c is a SCIENTIFIC DESIGN + SPECIFICATION + FREEZE task.

It must resolve exactly the implementation blockers A01–A17 recorded in:

    research/phase3/task86c-v2-scientific-impl/
        TASK86C_V2_SCIENTIFIC_CONTRACT_AMBIGUITY.md

The result must allow a subsequent implementation agent to implement
G1-v2 without making any independent scientific choices.

The required terminal product is:

    G1_V2_EXECUTABLE_SCIENTIFIC_CONTRACT_FROZEN

Task85c does NOT:

    implement the production scientific handlers;
    build the production scientific executable;
    execute Task86C-v2 blind controls;
    unblind controls;
    evaluate Voynich;
    modify previous scientific results;
    reinterpret Task86R/Task86C results.


======================================================================
1. BACKGROUND
======================================================================

Task85b froze the G1-v2 methodological design.

Task86C-v2-scientific-impl subsequently established:

    TASK86C_V2_SCIENTIFIC_EXECUTION_READY = NOT_SUPPORTED

    TERMINAL_MARKER =
        TASK86C_V2_SCIENTIFIC_CONTRACT_AMBIGUOUS

The implementation audit identified 17 independent blockers A01–A17.

The failure is not an experimental result.

It means that Task85b does not uniquely map:

    scientific design
        →
    executable algorithm
        →
    immutable scientific evidence.

Task85c must close that gap.


======================================================================

======================================================================

After Task85c, two competent independent implementers given only:

    Task85c frozen contract;
    immutable input artifacts;
    specified runtime boundary

must be able to produce scientifically equivalent implementations
without making additional scientific design decisions.

Where byte identity is required by the contract, the expected byte
representation must also be uniquely specified.

======================================================================
4. TASK85B RELATIONSHIP
======================================================================

Task85c does not discard Task85b.

Treat Task85b as the scientific parent design.

For every Task85c decision classify it as one of:

    CLARIFICATION
    COMPLETION
    NECESSARY_SCIENTIFIC_CHANGE

CLARIFICATION:
    makes an already unique Task85b intention executable.

COMPLETION:
    selects a missing parameter/algorithm required to instantiate
    Task85b without changing its intended scientific question.

NECESSARY_SCIENTIFIC_CHANGE:
    changes a substantive Task85b scientific choice because no
    satisfactory executable completion exists.

Every NECESSARY_SCIENTIFIC_CHANGE requires explicit documentation
and justification.

Do not hide changes under "implementation detail".

8. GOLDEN VECTOR RULE
======================================================================

Every scientifically relevant algorithm introduced or completed by
Task85c must have at least one deterministic golden test vector.

Prefer several vectors for important edge cases.

A golden vector must specify enough information to detect a
scientifically non-equivalent implementation.

Typical structure:

    input
    frozen parameters
    seed/domain if stochastic
    expected intermediate state where useful
    expected output
    expected status
    expected canonical representation/hash where applicable.

Golden vectors are part of the frozen scientific contract.
