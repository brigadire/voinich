Task85b — G1-v2 Measurement, Evidence and Distributed Execution Design


PURPOSE

Redesign the Phase III G1 token-formation experiment after the
negative methodological results of:

    Task86R
    Task85a-v1.1
    Task86C
    Task86C-a

and freeze a new G1-v2 experimental contract suitable for a new
blind positive-control experiment.

Task85b must solve three distinct problems:

1. SCIENTIFIC IDENTIFIABILITY

   G1-v1 returned NONE for every synthetic ground-truth class
   M0–M5 and for all natural-language controls.

   G1-v2 must be designed so that known generating mechanisms
   can in principle be recovered and distinguished.

2. EVIDENCE OBSERVABILITY

   Task86C-a established that the frozen Task86C artifacts do not
   retain enough intermediate evidence to reconstruct why models
   were rejected.

   G1-v2 must preserve the complete scientific decision path.

3. COMPUTATIONAL SCALABILITY

   Task86C required approximately 12 hours despite execution being
   distributed over two computers.

   G1-v2 experiments must support manifest-driven, resumable,
   horizontally scalable distributed computation, preferably
   reusing the distributed execution mechanism already developed
   and used in Phase I.

Task85b is a DESIGN / PREREGISTRATION task.

It must NOT execute the full new control experiment and must NOT
execute a new Voynich experiment.


======================================================================
1. SCIENTIFIC CONTEXT
======================================================================

Preserve the following historical results exactly.

Task86R:

    G1_MINIMAL_CLASS = NONE

but qualified by:

    TASK86R_CONFIRMATORY_INTEGRITY_QUALIFIED.

Task86C:

    synthetic M0–M5 recovery = 0;
    natural-language controls = NONE;
    G1_MEASUREMENT_IDENTIFIABLE = NOT_SUPPORTED;
    TASK86R_NONE_INTERPRETABILITY = NOT_INTERPRETABLE;
    G1_V2_REQUIRED = YES.

Task86C-a:

    TASK86C_A_EVIDENCE_INSUFFICIENT.

The Task86C-a result is important:

it does NOT establish that PM6 was the sole cause of failure.

The frozen artifacts do not preserve sufficient PM-by-PM and
F2-by-F2 evidence to determine latent adequacy or reconstruct
the exact rejection path.

Do not reinterpret these historical results.

2. AUTHORITATIVE REQUIREMENTS
======================================================================

Use as primary input:

    research/phase3/task86c-a/TASK85B_REQUIREMENTS.md
    research/phase3/task86c-a/G1_V2_REQUIREMENTS.tsv

and relevant frozen contracts/reports from:

    Task85

    Task86R
    Task86C
    Task86C-a.

At minimum preserve the requirements already identified by
Task86C-a:

1. Persist every PM value, baseline, frozen threshold,
   finite/availability flag and per-baseline gate outcome.

2. Separate PM6 construction availability, score validity and
   acceptance.

3. Persist every F2 metric/family result, generation-scale result

4. Separate model evidence from induction caps, convergence

6. Hash all per-job intermediate artifacts and make decision paths

7. Do not tune thresholds from Task86C controls and do not treat
   Task86C-a CF1/CF2 as scientific classifications.

Add the distributed-execution requirements defined below.


======================================================================
3. PRIMARY SCIENTIFIC QUESTION
======================================================================

G1-v2 must answer:

    What is the minimum tested model class sufficient to account
    for token formation under a validated and identifiable
    measurement protocol?

Formally:

    G1_MINIMAL_CLASS ∈
        {M0, M1, M2, M3, M4, M5, NONE, NOT_IDENTIFIABLE}

But unlike G1-v1:

    NONE

must mean:

    tested models were observed and validly rejected,

not:

    some required metric was unavailable,
    training did not converge,
    computation hit a cap,
    generation failed,
    or the decision path was not recorded.

NOT_IDENTIFIABLE must be a first-class result.


======================================================================
4. MODEL LADDER
======================================================================

Retain M0–M5 as the initial model ladder unless the audit reveals
a formal reason that a class cannot be evaluated under G1-v2.

Conceptual ladder:

    M0 — frequency / IID
    M1 — fixed-order local dependence
    M2 — variable-memory dependence
    M3 — deterministic finite-state
    M4 — probabilistic finite-state
    M5 — explicit component/rule grammar.

Task85b may correct implementation semantics where required by
the Task85a-v1.1 audit, but every such change must be explicitly
classified as:

    EQUIVALENT_IMPLEMENTATION

or:

    SCIENTIFIC_CHANGE.

Do not silently modify M0–M5.


======================================================================
5. MODEL CLASS VS INDUCTION ALGORITHM
======================================================================

G1-v2 must distinguish:

    MODEL_CLASS_INADEQUATE

from:

    INDUCTION_FAILED.

For M3/M4 in particular:

    failure of a state-merging algorithm;
    hitting an operation cap;
    failure to converge

must not automatically imply:

    finite-state class rejected.

Define separate statuses for:

    class evidence;
    fitting/induction evidence;
    computational completion.


======================================================================
6. MODEL STATUS TAXONOMY
======================================================================

Every candidate must terminate with a structured status.

At minimum distinguish:

    FITTED

    TRAINING_FAILED
    INDUCTION_LIMIT_REACHED
    CONVERGENCE_FAILED

    METRIC_AVAILABLE
    METRIC_UNAVAILABLE
    METRIC_NONFINITE

    PREDICTIVE_PASS
    PREDICTIVE_FAIL
    PREDICTIVE_NOT_ASSESSABLE

    GENERATION_SUCCESS
    GENERATION_FAILED
    GENERATION_NOT_REACHED

    STRUCTURAL_PASS
    STRUCTURAL_FAIL
    STRUCTURAL_NOT_ASSESSABLE

    MODEL_ADEQUATE
    MODEL_INADEQUATE
    MODEL_NOT_IDENTIFIABLE.

Do not collapse these into PASS/FAIL.


======================================================================
7. PREDICTIVE ADEQUACY REDESIGN
======================================================================

Audit the role of:

    PM1
    PM2
    PM4
    PM5
    PM6.

For each metric specify:

    scientific quantity measured;
    estimator;
    baseline;
    threshold;
    availability conditions;
    finite-value conditions;
    gate semantics;
    failure semantics.

The design must determine whether each PM is:

    REQUIRED_GATE

    SUPPORTING_EVIDENCE

    DIAGNOSTIC_ONLY.

Do not automatically retain the G1-v1 rule:

    all PMs must be available and pass.


======================================================================
8. PM6 REDESIGN
======================================================================

PM6 requires special treatment because Task86C showed widespread
negative-set exhaustion, while Task86C-a could not establish
whether PM6 alone caused the final failures.

Separate:

    PM6_CONSTRUCTION_AVAILABLE
    PM6_SCORE_VALID
    PM6_ACCEPTED.

Failure to construct a negative set must NOT automatically be
interpreted as evidence against the model.

Task85b must design a negative-token protocol that is:

    mathematically constructible;
    appropriate under alphabet saturation;
    applicable across corpus scales;
    applicable to synthetic controls;
    applicable to natural languages;
    applicable to Voynich without Voynich-specific tuning.

Possible alternatives may be evaluated in DESIGN work, but the
selected definition must be frozen before new blind controls.

Do not choose a PM6 replacement based on which one would make
Task86R or Task86C pass.


======================================================================
9. SATURATION ANALYSIS
======================================================================

The new negative-token protocol must explicitly model:

    token length;
    alphabet size;
    observed type saturation;
    candidate negative space.

Before confirmation, prove or empirically validate on development
controls that the requested negative sample is constructible.

If the valid negative space is insufficient, return:

    NEGATIVE_TEST_NOT_IDENTIFIABLE

rather than:

    MODEL_FAIL.


======================================================================
10. PREDICTIVE GATE SEMANTICS
======================================================================

Define three-valued or richer logic.

At minimum:

    PASS
    FAIL
    NOT_ASSESSABLE.

The overall predictive verdict must distinguish:

    actual evidence of predictive inadequacy

from:

    missing/unavailable measurement.

Define the complete truth table before execution.


======================================================================
11. STRUCTURAL ADEQUACY REDESIGN
======================================================================

Audit the existing F2 structural criteria.

For every retained F2 metric record:

    metric ID;
    family;
    computation;
    applicability;
    threshold;
    baseline;
    expected artifact;
    pass/fail/not-assessable semantics.

Preserve the Task85 observation that some F2 CORE metrics are
skeleton-only and therefore automatically matched by construction.

Such metrics must not count as independent evidence of model
adequacy.


======================================================================
12. F2 EVIDENCE PRESERVATION
======================================================================

For every evaluated candidate persist:

    each individual F2 value;
    corresponding target/control value;
    distance/effect;
    threshold;
    family result;
    scale result;
    replicate result;
    applicability;
    NOT_REACHED reason.

Never persist only:

    StructuralAdequacy = FAIL.


======================================================================
13. STRUCTURAL GATE LOGIC
======================================================================

Define before execution:

    metric-level decision;
    family-level decision;
    multi-family decision;
    scale aggregation;
    replicate aggregation.

A metric being unavailable must not silently become FAIL.

A structural stage not executed must be:

    NOT_REACHED

rather than:

    FAIL.


======================================================================
14. COMPLEXITY AND MINIMALITY
======================================================================

Define how minimal adequate class is selected.

The procedure must distinguish:

    multiple adequate classes;
    observational equivalence;
    insufficient discrimination;
    true minimal class.

Possible outputs must include:

    UNIQUE_MINIMUM
    EQUIVALENT_SET
    ORDER_ONLY
    NOT_IDENTIFIABLE.

Do not force a single M0–M5 winner when the evidence only supports
an equivalence class.


======================================================================
15. MODEL RECOVERY REQUIREMENT
======================================================================

A measurement system intended to identify M0–M5 must first prove
that it can recover known mechanisms.

Therefore G1-v2 cannot be opened on Voynich until a separate new
blind control experiment demonstrates acceptable recovery.

Task85b must define quantitative recovery requirements.


======================================================================
16. SYNTHETIC POSITIVE CONTROLS
======================================================================

The future control experiment must contain new synthetic controls.

Do NOT reuse the exact Task86C synthetic populations as the only
confirmatory controls because their results are already known.

Use new blind generators/parameters/seeds.

Include:

    M0
    M1
    M2
    M3
    M4
    M5.

Prefer multiple independent generators per class.

Ground truth must remain hidden until analysis freeze.


======================================================================
17. INDEPENDENT GENERATORS
======================================================================

Primary validation must use generators independent from the
production fitting implementation.

Avoid:

    model implementation testing itself.

For every synthetic generator freeze:

    generator definition;
    theoretical class;
    minimal sufficient class;
    parameters;
    seed;
    implementation hash.


======================================================================
18. RECOVERY CRITERIA
======================================================================

Preregister quantitative criteria for:

    exact-class recovery;
    minimal-sufficient recovery;
    equivalence-compatible recovery;
    NONE rate;
    NOT_IDENTIFIABLE rate;
    underfitting;
    over-complexity.

The criteria must be frozen before synthetic unblinding.


======================================================================
19. NATURAL-LANGUAGE CONTROLS
======================================================================

Retain natural-language positive controls.

At minimum include typologically distinct languages such as:

    English;
    Latin;
    Sanskrit

or justified replacements/additions.

Task85b must define corpus provenance, tokenization, scale matching
and sampling rules.

The goal is not to discover the true linguistic grammar of those
languages.

The goal is to establish that G1-v2 can produce meaningful,
non-degenerate adequacy results on ordinary natural token systems.


======================================================================
20. NO CONTROL TUNING
======================================================================

Distinguish:

    DEVELOPMENT CONTROLS

from:

    CONFIRMATORY BLIND CONTROLS.

Task85b may use old Task86C results to understand defects.

It may use explicitly designated development data to develop the
new measurement system.

But final validation must use unseen/frozen blind controls.

Do not tune thresholds on confirmatory controls.


======================================================================
21. VOYNICH FIREWALL
======================================================================

No Voynich data may be used to:

    choose PM definitions;
    choose thresholds;
    select negative-token protocol;
    choose F2 gates;
    choose model parameters;
    tune induction;
    choose recovery criteria.

G1-v2 must first pass its positive controls.

Only then may a separate future task open Voynich.


======================================================================
22. COMPLETE EVIDENCE CHAIN
======================================================================

The central G1-v2 reproducibility requirement is:

    every final scientific verdict must be reconstructible
    without rerunning fitting or generation.

For every candidate preserve:

INPUT
  ↓
FIT / INDUCTION
  ↓
MODEL ARTIFACT
  ↓
PM1...PMn
  ↓
INDIVIDUAL PREDICTIVE GATES
  ↓
PREDICTIVE VERDICT
  ↓
GENERATED ARTIFACTS
  ↓
F2 METRICS
  ↓
F2 FAMILY GATES
  ↓
STRUCTURAL VERDICT
  ↓
COMPLEXITY / MINIMALITY
  ↓
FINAL VERDICT.


======================================================================
23. INTERMEDIATE ARTIFACT CONTRACT
======================================================================

For every scientific intermediate artifact record:

    artifact ID;
    producing job;
    input hashes;
    code hash;
    config hash;
    seed where applicable;
    artifact hash;
    scientific meaning.

The final results manifest must transitively cover the entire
evidence graph.


======================================================================
24. DECISION-PATH REGENERATION
======================================================================

Create a verifier capable of rebuilding all:

    metric gates;
    family gates;
    adequacy gates;
    minimality decisions;
    final verdicts

using only frozen intermediate artifacts.

It must NOT invoke:

    fitting;
    model induction;
    corpus generation.

This is a mandatory acceptance test for G1-v2.


======================================================================
25. NEGATIVE VERIFIER TESTS
======================================================================

The verifier must fail if, for example:

    one PM value is missing;
    one threshold differs;
    one artifact hash changes;
    one F2 result disappears;
    one unavailable metric is silently treated as FAIL;
    one model failure is substituted for induction failure.

Include automated negative tests.


======================================================================
26. DISTRIBUTED COMPUTATION REQUIREMENT
======================================================================

G1-v2 must support horizontally scalable distributed execution.

Motivation:

    Task86C:
        672 jobs;
        4032 model executions;
        approximately 12 hours wall-clock;
        two computing nodes.

Future G1-v2 controls may be at least as expensive.

Distributed execution is therefore part of the required
experimental infrastructure.


======================================================================
27. REUSE PHASE-I DISTRIBUTED MECHANISM
======================================================================

Before implementing new distributed infrastructure:

    locate the distributed computation mechanism used for
    computationally expensive Phase-I experiments;

    document its architecture;

    identify reusable components;

    determine whether it supports the requirements below.

Prefer extending/reusing that mechanism.

Do not build a parallel scheduler unless the existing mechanism
cannot satisfy G1-v2 requirements.

Create:

    PHASE1_DISTRIBUTED_EXECUTION_AUDIT.md.


======================================================================
28. EXECUTION ARCHITECTURE
======================================================================

Target architecture:

                 SCIENTIFIC MANIFEST
                         │
                         ▼
                      JOB DAG
                         │
                         ▼
                  DISTRIBUTED QUEUE
                   /      |      \
                  /       |       \
             worker1   worker2   workerN
                  \       |       /
                   \      |      /
                         ▼
                IMMUTABLE RESULTS
                         │
                         ▼
                      VERIFIER
                         │
                         ▼
                     AGGREGATOR.

Distributed executor must contain no scientific decision logic.


======================================================================
29. N-WORKER MODEL
======================================================================

Do not design specifically for:

    local + 10.10.24.105.

These are currently available workers, but the architecture must
support:

    1 orchestrator + N workers.

Current expected workers include:

    local node;
    10.10.24.105.

Additional compatible workers must be addable without modifying
the scientific manifest.


======================================================================
30. JOB GRANULARITY
======================================================================

Avoid large static assignments such as:

    node A → half experiment
    node B → other half.

Decompose computation into sufficiently small independent jobs.

Candidate dimensions include:

    corpus;
    split;
    model;
    candidate/hyperparameter;
    scale;
    replicate;
    seed;
    generation batch;
    structural evaluation stage.

Exact granularity must preserve scientific semantics.

A job should be small enough to avoid multi-hour stragglers where
further scientifically valid decomposition is possible.


======================================================================
31. DYNAMIC SCHEDULING
======================================================================

Use dynamic scheduling / queue claiming / work stealing if
supported by the Phase-I mechanism.

When a worker completes a job, it should obtain another pending
job.

This is particularly important because runtime is expected to
differ strongly between:

    M0/M1
    M2
    M3/M4
    M5.


======================================================================
32. JOB IDENTITY
======================================================================

Every job must have a deterministic job_id derived from its
scientific configuration.

At minimum include relevant:

    experiment;
    protocol version;
    corpus ID;
    model;
    candidate;
    scale;
    replicate;
    seed;
    stage.

Worker identity must NOT affect job_id.


======================================================================
33. IMMUTABLE JOB BUNDLES
======================================================================

Each worker receives an immutable job definition containing:

    job_id;
    input artifact hashes;
    code/executable hash;
    config hash;
    seed;
    dependency hashes;
    expected output schema.

Workers must not modify:

    scientific manifest;
    input corpora;
    frozen design;
    thresholds;
    registries.


======================================================================
34. RESUMABILITY
======================================================================

Long experiments must be safely resumable.

Completed and verified jobs must never be recomputed merely because:

    orchestrator restarted;
    worker disappeared;
    SSH session failed;
    another worker was added.

Pending/infrastructure-failed jobs may be reassigned.


======================================================================
35. SCIENTIFIC VS INFRASTRUCTURE FAILURE
======================================================================

Explicitly distinguish:

SCIENTIFIC:

    TRAINING_FAILED
    INDUCTION_LIMIT_REACHED
    CONVERGENCE_FAILED
    NUMERICALLY_UNSTABLE
    GENERATION_FAILED
    METRIC_UNAVAILABLE

from INFRASTRUCTURE:

    WORKER_LOST
    SSH_FAILURE
    PROCESS_INTERRUPTED
    RESULT_TRANSFER_FAILED
    STORAGE_FAILURE.

Scientific failures are results.

Infrastructure failures may be retried with identical job identity.


======================================================================
36. CROSS-NODE DETERMINISM
======================================================================

Before bulk execution, representative jobs must run on multiple
nodes.

Include at least representatives of:

    M0/M1
    M2
    M3
    M4
    M5.

Prefer byte-identical scientific artifacts.

If byte identity is impossible due to justified floating-point
differences, define canonical representation and numerical
equivalence before execution.

Do not invent tolerance after observing differences.


======================================================================
37. DUPLICATE EXECUTION
======================================================================

The scheduler may deliberately execute selected jobs on multiple
workers.

If results are identical:

    record reproducibility confirmation.

If results conflict:

    quarantine all conflicting copies.

Never choose one result because it appears preferable.


======================================================================
38. DAG EXECUTION
======================================================================

Support explicit dependencies between stages, e.g.:

    FIT
      ↓
    PREDICTIVE
      ↓
    GENERATION
      ↓
    STRUCTURAL
      ↓
    AGGREGATION.

But scientific design determines whether downstream stages may be
skipped.

Do not let executor policy decide scientific reachability.


======================================================================
39. EVIDENCE COLLECTION AND EARLY STOPPING
======================================================================

G1-v1 lost evidence partly because aggregate gates obscured
intermediate results.

Therefore early stopping must be explicitly designed.

For each stage determine whether failure permits skipping later
scientific computations.

If skipped, preserve:

    NOT_REACHED
    reason
    upstream gate
    dependency.

Where diagnostic evidence is required for validation, compute it
even if the final candidate is already known to be inadequate.


======================================================================
40. PERFORMANCE TELEMETRY
======================================================================

Record operationally for each job:

    worker;
    start time;
    end time;
    wall time;
    CPU time;
    peak memory;
    retry count;
    infrastructure status.

Operational telemetry must not alter scientific outcomes.


======================================================================
41. RUNTIME MODEL
======================================================================

Use development runs to estimate runtime by:

    model class;
    scale;
    stage.

Use runtime predictions only for scheduling and load balancing.

Do not change scientific thresholds or computation limits based on
confirmatory runtime observations.


======================================================================
42. STRAGGLER ANALYSIS
======================================================================

Identify which G1-v2 stages can create long-tail jobs.

Especially audit:

    M3/M4 induction;
    M5 fitting;
    generation;
    F2 structural extraction.

Where scientifically possible, design finer decomposition.

Where decomposition is impossible, document the limitation.


======================================================================

Every distributed result must include:

    job_id;
    worker;
    input hashes;
    code hash;
    config hash;
    seed;
    dependency hashes;
    scientific status;
    infrastructure status;
    artifact hashes.

======================================================================
44. DISTRIBUTED VERIFIER
======================================================================

Before aggregation verify:

    all required jobs accounted for;
    no unresolved duplicate conflicts;
    hashes valid;
    inputs correct;
    code revision correct;
    config correct;
    seeds correct;
    dependencies correct;
    evidence artifacts complete;
    no post-freeze scientific configuration introduced.

Aggregation must refuse incomplete/unresolved manifests.


======================================================================
45. HORIZONTAL SCALABILITY TEST
======================================================================

Before the full future Task86C-v2 experiment, define a small
representative benchmark manifest.

Run with different worker counts where resources permit.

Measure:

    wall-clock time;
    worker utilization;
    scheduling overhead;
    straggler contribution.

Task85b must preregister a reasonable scalability acceptance
criterion.

The criterion need not require perfect linear speedup.
