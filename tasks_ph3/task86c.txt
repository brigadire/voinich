Task86C — G1 Model-Recovery and Natural-Language Control Validation

Цель

Проверить валидность и идентифицируемость экспериментального аппарата
G1, использованного в Task86R, до проведения любых новых экспериментов
над Voynich Manuscript.

Основные вопросы:

1. Способен ли G1 pipeline распознавать известные generating mechanisms
   M0–M5 на synthetic corpora с известной ground truth?

2. Способна ли хотя бы одна из моделей M0–M5 пройти G1 adequacy
   criteria на обычных естественных языках?

3. Является ли результат

       G1_MINIMAL_CLASS = NONE

   специфическим для Voynichese или такой же результат возникает
   на positive controls?

4. Является ли обнаруженная в Task86R невозможность PM6
   Voynich-specific phenomenon или общим дефектом
   negative-token measurement protocol?

5. Обладает ли существующий G1 apparatus достаточной sensitivity
   и specificity, чтобы его результаты на Voynich вообще можно было
   интерпретировать как evidence о token-formation mechanism?

Task86C является CONTROL / VALIDATION experiment.

Task86C НЕ является:

    новым Voynich experiment;
    исправлением Task86R;
    G1-v2;
    разработкой новой grammar;
    tuning M0–M5;
    tuning adequacy gates.

Voynich corpus НЕ использовать для model fitting, threshold selection,
control selection или изменения protocol.


======================================================================
1. RELATION TO TASK86R
======================================================================

Task86R сохраняется как исторический результат:

    TOKEN_GRAMMAR_FROZEN

с qualification:

    TASK86R_CONFIRMATORY_INTEGRITY_QUALIFIED.

Task86C не должен изменять его artifacts или verdicts.

Task86C должен определить, насколько measurement apparatus,
использованный в Line A, вообще способен:

    recover known model classes;

    recognize ordinary structured token systems;

    distinguish structured systems from simpler null systems.

Task86C является validation experiment над методом,
а не над Voynich.


======================================================================
2. SCIENTIFIC FIREWALL
======================================================================

До freeze Task86C design запрещено использовать:

    Voynich corpus;
    Voynich F2 values;
    Task86R HELDOUT values;
    Voynich-specific thresholds;
    Voynich-specific failure patterns

для выбора:

    control corpora;
    corpus sizes;
    model parameters;
    generator parameters;
    recovery thresholds;
    adequacy modifications.

Из Task86R разрешено знать только methodological facts,
необходимые для постановки validation:

    G1_MINIMAL_CLASS = NONE;
    PM6 negative construction became impossible;
    Task85a-v1.1 audit found execution/provenance issues.

Не оптимизировать Task86C так, чтобы "починить" Voynich result.


======================================================================
3. TWO INDEPENDENT EXPERIMENTAL BRANCHES
======================================================================

Task86C состоит из двух основных ветвей:

    Branch S — Synthetic Model Recovery

    Branch N — Natural-Language Positive Controls.

Обе обязательны.

Дополнительно:

    Branch P — Protocol Failure Diagnostics

для анализа PM6 и других measurement failures.


======================================================================
4. BRANCH S — SYNTHETIC MODEL RECOVERY
======================================================================

Создать synthetic corpora с известной generating ground truth:

    S0 generated by M0-like process
    S1 generated by M1-like process
    S2 generated by M2-like process
    S3 generated by M3-like process
    S4 generated by M4-like process
    S5 generated by M5-like process.

Ground-truth labels должны быть известны generator stage,
но analysis pipeline должен работать blind относительно labels.


======================================================================
5. DO NOT TEST IMPLEMENTATION AGAINST ITSELF
======================================================================

Для каждого model class по возможности использовать два generator types:

A. IN_FAMILY

    generator использует production/frozen implementation
    соответствующего model family.

B. INDEPENDENT

    independently implemented generator,
    не использующий fitting/generation code исследуемой M0–M5 model.

Primary recovery evidence:

    INDEPENDENT generators.

IN_FAMILY используется как sanity/lower-bound control.


======================================================================
6. INDEPENDENT GENERATORS
======================================================================

Минимальные требования:

M0:

    independent IID categorical glyph generator.

M1:

    independently implemented fixed-order Markov generator.

M2:

    independently implemented variable-context generator,
    например explicit context tree with known variable depths.

M3:

    manually specified deterministic finite-state token generator.

M4:

    manually specified probabilistic finite-state generator.

M5:

    manually specified component/slot/rule grammar
    with productive recombination.

Independent generators не должны вызывать production M0–M5 fitting code.


======================================================================
7. MULTIPLE GENERATORS PER CLASS
======================================================================

Не использовать один synthetic mechanism как представитель класса.

Для каждого M0–M5 создать несколько independently parameterized
ground-truth mechanisms.

Минимум:

    3 mechanisms per class.

Желательно:

    5 mechanisms per class

если computational budget позволяет.

Parameters определить и freeze до execution.


======================================================================
8. CORPUS SCALE
======================================================================

Synthetic corpora должны включать несколько размеров.

Минимум:

    SMALL
    MEDIUM
    VOYNICH_SCALE
    LARGE.

VOYNICH_SCALE должен быть сопоставим по token count
с корпусом, использованным в Task86R.

Конкретные размеры определить до execution
и зафиксировать в design.

Цель:

    измерить зависимость recoverability
    от corpus size.

Не подбирать scale по результатам recovery.


======================================================================
9. REPLICATES
======================================================================

Для каждого:

    generator
    ×
    scale

создать несколько independent corpus replicates.

Минимум:

    8.

Предпочтительно:

    16

если вычислительная стоимость допустима.

Seed registry должен быть frozen до execution.


======================================================================
10. SYNTHETIC BLIND MANIFEST
======================================================================

Создать два manifest:

    SYNTHETIC_GENERATION_MANIFEST

и:

    SYNTHETIC_ANALYSIS_MANIFEST.

Analysis manifest не должен содержать human-readable ground-truth class.

Использовать opaque corpus IDs.

Ground truth открыть только после завершения и freeze
analysis results.


======================================================================
11. RECOVERY OUTPUT
======================================================================

Для каждого synthetic corpus определить:

    recovered adequate models;
    minimal adequate model;
    G1_MINIMAL_CLASS;
    TOKEN_FORMATION_DEPTH;
    failure reasons.

После unblinding сравнить с ground truth.

Отдельно:

======================================================================
13. RECOVERY SHOULD RESPECT MODEL LADDER
======================================================================

Exact class equality является сильнейшим результатом,
но дополнительно оценить ladder-compatible recovery.

Например, если corpus generated by M4
может быть полностью описан более простой M2,
это не обязательно ошибка classifier.

Поэтому различать:

    EXACT_RECOVERY

и:

    MINIMAL_SUFFICIENT_RECOVERY.

Для каждого synthetic ground-truth generator определить,
какой минимальный класс теоретически способен породить
его distribution.

Это значение freeze вместе с generator definition.


======================================================================
14. SYNTHETIC PRIMARY METRICS
======================================================================

Вычислить минимум:

    exact recovery rate;
    minimal-sufficient recovery rate;
    NONE rate;
    INCONCLUSIVE rate;
    false-complexity rate;
    underfit rate;
    recovery by corpus scale.

Особенно:

    P(NONE | known M0–M5 generator).


======================================================================
15. SYNTHETIC SUCCESS CRITERION
======================================================================

До unblinding определить quantitative criterion,
при котором G1 считается model-recovery capable.

Не придумывать threshold после просмотра confusion matrix.

Критерий должен отдельно учитывать:

    exact recovery;
    ladder-compatible/minimal recovery;
    catastrophic NONE rate.

Если известные generators систематически дают NONE,
measurement system не может считаться validated.


======================================================================
16. BRANCH N — NATURAL-LANGUAGE CONTROLS
======================================================================

Использовать реальные natural-language corpora.

Минимум:

    English;
    Latin.

Желательно добавить третий язык
с существенно отличающейся морфологической типологией,
например агглютинативный язык.

Конкретный третий язык выбирать по:

    corpus availability;
    licensing;
    tokenization quality;
    provenance;

а не по ожидаемому результату G1.


======================================================================
17. ENGLISH CONTROL
======================================================================

Разрешено использовать Doyle corpus,
уже применявшийся в предыдущих фазах,
если его provenance/licensing удовлетворяют repository policy.

Не использовать только один текст,
если доступен достаточно большой corpus.

Желательно несколько произведений/авторов
для проверки author dependence.


======================================================================
18. LATIN CONTROL
======================================================================

Использовать полноценный Latin natural-language corpus.

Не использовать Burchards abbreviation representation
как единственный Latin control:

    shorthand corpus является специальным notation control,
    а не обычным natural-language baseline.

Latin control должен содержать normal expanded/tokenized Latin.


======================================================================
19. NATURAL-LANGUAGE CORPUS PROVENANCE
======================================================================

Для каждого corpus сохранить:

    source;
    version;
    download location;
    license;
    checksum;
    acquisition date;
    preprocessing;
    tokenization;
    exclusions.

Не включать corpus в public repository,
если license этого не позволяет.

В таком случае сохранить reproducible acquisition instructions.


======================================================================
20. NATURAL-LANGUAGE SIZE MATCHING
======================================================================

Размер корпуса является потенциальным confound.

Для каждого natural-language corpus создать
детерминированные subsamples размеров,
соответствующих synthetic scale grid.

Особенно обязательно:

    VOYNICH_SCALE.

Использовать несколько independent deterministic samples,
если corpus достаточно велик.


======================================================================
21. NATURAL-LANGUAGE QUESTION
======================================================================

Branch N НЕ пытается определить
"истинную грамматику английского или латыни".

Основной вопрос:

    существует ли хотя бы один M0–M5 candidate,
    который существующий G1 apparatus признаёт adequate
    для ordinary natural-language token formation?

Primary output:

    NATURAL_LANGUAGE_G1_APPLICABILITY =
        SUPPORTED
        / PARTIAL
        / NOT_SUPPORTED.


======================================================================
22. NATURAL-LANGUAGE EXPECTATION
======================================================================

Не preregister:

    English must be M2;
    Latin must be M5;

Это было бы необоснованно.

Допустимы:

    M1;
    M2;
    M3;
    M4;

Критически важный результат:

    repeated NONE across ordinary languages.


======================================================================
23. CROSS-LANGUAGE STABILITY
======================================================================

Определить:

    language;
    corpus;
    author;
    scale

effects.

Не требовать одинакового minimal class
для разных языков.

Проверить, является ли:

    NONE

систематическим результатом measurement apparatus.


======================================================================
24. BRANCH P — PM6 PROTOCOL DIAGNOSTICS
======================================================================

На каждом synthetic и natural-language corpus
выполнить frozen Task86R negative-token protocol
БЕЗ ИЗМЕНЕНИЙ.

Зафиксировать:

    requested negatives;
    constructible negatives;
    exhaustion by token length;
    alphabet saturation;
    attempt exhaustion;
    rejection reasons.


======================================================================
25. DO NOT FIX PM6 IN TASK86C
======================================================================

В primary Task86C experiment запрещено:

    менять negative sampler;
    исключать singleton tokens;
    увеличивать attempt cap;
    менять matching;
    вводить edit-distance negatives;
    вводить generated pseudo-words.

Цель — проверить существующий measurement protocol.

Возможные улучшения можно описать только
как recommendations for G1-v2.

======================================================================
28. HISTORICAL G1 PROTOCOL VS AUDITED IMPLEMENTATION
======================================================================

Task85a-v1.1 обнаружил scientific changes
в историческом Task86R implementation.

Task86C не должен молча выбирать одну из версий.

До execution определить два слоя:

A. HISTORICAL_REPLICATION

    максимально точно воспроизводит фактический Task86R apparatus,
    необходимый для вопроса:
    "что сделал бы тот же measurement system на controls?"

B. CONTRACT_REFERENCE

    использует intended frozen Task85/85a semantics
    там, где они однозначно определены.

Если выполнение CONTRACT_REFERENCE невозможно
из-за incomplete contract:

    пометить соответствующую branch как NOT_EXECUTABLE.

Не доопределять её post hoc.


======================================================================
29. PRIMARY CONTROL QUESTION
======================================================================

Для оценки интерпретируемости исторического Voynich result
PRIMARY является:

    HISTORICAL_REPLICATION.

Потому что вопрос:

    даёт ли apparatus, реально породивший
    G1_MINIMAL_CLASS=NONE на Voynich,
    тот же результат на controls?


======================================================================
30. NO VOYNICH EXECUTION
======================================================================

Task86C не должен повторно вычислять G1 на Voynich.

Разрешено использовать только frozen Task86R summary/result
для финального сравнительного контекста.

Не открывать Voynich corpus в analysis jobs.

Добавить automated Voynich-path firewall,
аналогично предыдущим target-blind tasks.


======================================================================
31. DISTRIBUTED EXECUTION
======================================================================

Task86C должен поддерживать распределённое выполнение
independent jobs минимум на:

    primary/local node

и:

    10.10.24.105.

Scientific result не должен зависеть от worker assignment.


======================================================================
32. EXECUTION ARCHITECTURE
======================================================================

Использовать manifest-driven execution.

Каждый job должен быть self-contained:

    immutable input;
    immutable config;
    explicit seed;
    explicit code revision;
    expected output paths.

Рекомендуемая схема:

    task86c-plan
        →
    TASK86C_JOB_MANIFEST.tsv
        →
    task86c-worker
        →
    per-job immutable result directories
        →
    task86c-aggregate
        →
    frozen aggregate results.


======================================================================
33. JOB IDENTITY
======================================================================

job_id должен детерминированно зависеть минимум от:

    experiment branch;
    corpus/generator ID;
    generator variant;
    scale;
    replicate;
    model candidate;
    protocol layer;
    seed/config identity.

Одинаковый logical job не должен
получать разные IDs на разных nodes.


======================================================================
34. NODE INDEPENDENCE
======================================================================

Запуск одного job на:

    local

и:

    10.10.24.105

при одинаковых:

    input bytes;
    executable/source revision;
    config;
    seed

должен давать byte-identical scientific artifact
или заранее определённую numerically equivalent representation.

Предпочтительно требовать byte-identical output.


======================================================================
35. DISTRIBUTED PRE-FLIGHT
======================================================================

До большого запуска выполнить cross-node reproducibility test.

Минимум по одному representative job из:

    synthetic M0;
    synthetic M2;
    synthetic M4;
    synthetic M5;
    English;
    Latin.

Каждый выполнить на обоих nodes.

Сравнить:

    result hashes;
    model hashes;
    metric outputs;
    failure statuses.

Если scientific outputs расходятся:

    STOP DISTRIBUTED EXECUTION.

Не агрегировать mixed-node results.

======================================================================
39. REMOTE EXECUTION SAFETY
======================================================================

Не требовать shared mutable filesystem.

Предпочтительно:

    execute;
    produce result bundle;
    verify checksums;
    copy result back.

Remote node не должен изменять:

    manifests;
    source;
    frozen design;
    input corpora;
    aggregate tables.


======================================================================
40. RESUMABILITY
======================================================================

Pipeline должен поддерживать:

    interrupted execution;
    resume;
    retry failed infrastructure job;
    relocation job to another node.

Scientific failure и infrastructure failure
должны различаться.

Например:

    TRAINING_FAILED

не должен автоматически retry.

Но:

    SSH_CONNECTION_LOST

может быть retried с тем же job_id/config/seed.


======================================================================
41. DUPLICATE EXECUTION
======================================================================

Если один job выполнен на двух nodes:

    identical hashes
        →
    accept one, record duplicate verification;

    different hashes
        →
    quarantine both and investigate.

Нельзя выбирать "лучший" результат.

======================================================================
46. PRIMARY DECISION MATRIX
======================================================================

Task86C должен различать минимум четыре сценария:

CASE A:

    synthetic recovery good
    AND
    natural languages adequate

Verdict:

    G1 apparatus broadly validated.

Voynich NONE становится потенциально
специфическим и требует clean validation experiment.


CASE B:

    synthetic recovery good
    BUT
    natural languages mostly NONE

Verdict:

    model classes can recover themselves,
    but G1 is not validated for natural-language token systems.


CASE C:

    synthetic recovery poor

Verdict:

    G1 model ladder/measurement apparatus
    is not identifiable even on known ground truth.


CASE D:

    results dominated by PM6/protocol impossibility

Verdict:

    G1 measurement protocol invalid/inadequate
    for the intended comparison.
