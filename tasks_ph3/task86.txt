Task86 — Voynich Token-Formation Grammar Discovery
and Held-Out Validation

Цель

Выполнить первый эксперимент Line A Phase III:

    G1 — TOKEN FORMATION.

Используя полностью замороженный Task85 experimental contract,
определить, может ли внутренняя структура Voynich TOKENs быть
описана компактной формальной генеративной моделью, устойчивой:

    - на ранее не использованных данных;
    - между ZL3b и IT2a;
    - при независимой генерации synthetic token populations;
    - относительно заранее определённых baselines/nulls.

Основной исследовательский вопрос:

    Какой минимальный класс G1-модели достаточен
    для объяснения наблюдаемого token-formation fingerprint
    Voynichese?

В частности, необходимо определить, требуется ли для этого
явная rule/component grammar, либо наблюдаемая структура уже
объясняется более простыми моделями:

    IID/frequency
        →
    fixed-order Markov
        →
    variable-order Markov
        →
    deterministic finite-state
        →
    probabilistic finite-state
        →
    component/rule grammar.

Task86 НЕ исследует:

    G2 contextual sequence grammar;
    G3 manuscript structural conditioning;
    semantics;
    plaintext;
    natural-language status;
    Fontana/external-memory mechanisms;
    shorthand/acrostic hypotheses;
    information residual;
    message-free reproduction of the full manuscript.

Финальный результат:

    TOKEN_GRAMMAR_FROZEN

или, если G1 не может быть корректно идентифицирован:

    TOKEN_GRAMMAR_INCONCLUSIVE

или, если frozen Task85 contract невозможно выполнить
без существенного изменения scientific design:

    TASK86_EXPERIMENT_BLOCKED.

6. IMPLEMENT MODEL CLASSES M0–M5
======================================================================

Реализовать/использовать ровно frozen G1 model space.

M0
    IID / token-frequency baseline.

M1
    fixed-order GLYPH n-gram.

M2
    variable-order Markov.

M3
    deterministic finite-state formation model.

M4
    probabilistic finite-state formation model.

M5
    component/rule formation grammar.

Использовать только hyperparameter spaces,
зафиксированные в:

    GRAMMAR_MODEL_REGISTRY.tsv.

Не добавлять новые model classes после начала fitting.

======================================================================
8. M0 — FREQUENCY MODEL
======================================================================

M0 является нижней границей.

Проверить, какую часть observed G1 behavior
можно получить только из marginal frequencies.

M0 должен участвовать в:

    predictive comparison;
    complexity comparison;
    negative-token discrimination;
    generation validation.

Не трактовать плохой M0 fit как доказательство grammar.


======================================================================
9. M1 — FIXED-ORDER MARKOV
======================================================================

Исследовать frozen range orders/smoothing.

Model selection выполнять только на VALIDATION.

Не выбирать n после HELDOUT.

Отдельно сохранить dependence:

    order
        →
    predictive gain
        →
    Complexity(G).


======================================================================
10. M2 — VARIABLE-ORDER MARKOV
======================================================================

Проверить, даёт ли variable context существенное преимущество
над M1 при учёте complexity.

Ключевое сравнение:

    M1 vs M2.

Если дополнительная память M2 не даёт устойчивого выигрыша,
это должно быть сохранено как отрицательный результат.


======================================================================
11. M3 — DETERMINISTIC FINITE-STATE
======================================================================

Построить deterministic finite-state formation model
строго по frozen induction/hyperparameter contract.

Проверить:

    number of states;
    transitions;
    accepted/generated forms;
    held-out coverage;
    unseen-form behavior;
    Complexity(G).

Не интерпретировать states как linguistic categories.


======================================================================
12. M4 — PROBABILISTIC FINITE-STATE
======================================================================

Расширить M3 вероятностной структурой согласно frozen registry.

Ключевой вопрос:

    даёт ли probabilistic state structure
    explanatory compression относительно Markov models?

Сравнивать одновременно:

    predictive performance
    и
    Complexity(G).


======================================================================
13. M5 — COMPONENT/RULE GRAMMAR
======================================================================

Построить explicit component/rule formation grammar
в пределах frozen hyperparameter space.

COMPONENT не является morpheme.

Rule не является linguistic grammatical rule.

Проверить:

    component inventories;
    slot/rule structure;
    productive coverage;
    lexical exceptions;
    structural exceptions;
    unseen-form generalization;
    Complexity(G).

Особенно строго учитывать:

    LexiconCost
    и
    ExceptionCost.

M5 не может считаться compact,
если компактность получена ценой memorized lexicon.

14. FIT BOTH TRANSCRIPTIONS INDEPENDENTLY

Полный protocol выполнить независимо для:

Для каждого сравнения выдать:

16. VALIDATION STAGE
======================================================================

На VALIDATION выполнить:

    stability analysis.

frozen model classes, а не только лучший.


======================================================================
17. PREDICTIVE METRICS
======================================================================

Использовать frozen PM metrics.

Минимум:

    PM0 — training diagnostic only;
    PM1 — held-out NLL;
    PM2 — cross entropy;
    PM3 — perplexity where comparable;
    PM4 — unseen-form probability;
    PM5 — predictive calibration;
    PM6 — negative-token discrimination AUC.

До scoring явно зафиксировать scored unit.

Для G1 предпочтительно GLYPH-level scoring,
как предписано TASK86_HANDOFF.

Если TOKEN probability вычисляется корректной
маргинализацией G1 model, документировать метод.


======================================================================
18. NEGATIVE TOKEN TEST
======================================================================

Использовать frozen negative-token protocol.

Negative controls должны быть matched минимум по:

    TOKEN length

и, где применимо:

    GLYPH-frequency class;
    COMPONENT inventory.

Uniform random garbage использовать запрещено.

Проверить способность модели различать:

    observed held-out forms

от

    matched unobserved controls.

32. G1 MINIMALITY
======================================================================

Если существует хотя бы одна модель,
удовлетворяющая frozen adequacy gates:

    G1_min =
        argmin Complexity(G)

        subject to:

            PredictiveAdequacy(G)
            AND
            StructuralAdequacy(G).

Если несколько models statistically indistinguishable
и complexity difference недостаточно определён,
не выбирать победителя произвольно.

Разрешён verdict:

    G1_MINIMAL_CLASS = INCONCLUSIVE.

======================================================================

    M1 → M2

36. CROSS-TRANSCRIPTION MODEL STRUCTURE
======================================================================

Помимо metric agreement сравнить,
насколько selected models структурно совместимы
между ZL3b и IT2a.

Сравнивать только representation-invariant quantities,
например:

    model class;
    effective memory/order;
    state/rule complexity;
    normalized complexity;
    productivity behavior.

Не требовать literal equality states/rules,
поскольку transcription alphabets различаются.

38. DETERMINISM
======================================================================

должны иметь deterministic ordering.

confirmatory run не замораживать.

======================================================================
44. INTERPRETATION BOUNDARY
======================================================================

Даже сильный результат:

    G1_MINIMAL_CLASS = M5

не означает:

    Voynichese является языком;
    COMPONENT является морфемой;
    rule является грамматическим правилом языка;
    manuscript содержит semantic message.

Аналогично результат:

    G1_MINIMAL_CLASS = M1

или M2

не означает:

    manuscript meaningless;
    manuscript generated randomly.

Task86 отвечает только на вопрос
о минимальной формальной сложности
TOKEN FORMATION.


======================================================================
45. TASK87 HANDOFF
======================================================================

TASK87_HANDOFF.md должен передать:

    frozen G1 model(s);
    exact model artifacts;
    checksums;
    complexity;
    predictive results;
    structural results;
    transcription stability;
    failure ledger;
    unresolved G1 properties.

Особенно важно передать:

    G1_min

или, если он не идентифицирован:

    полный equivalence/viable set,
    а не искусственно выбранного winner.

Task87 должен строить G2 только поверх
frozen G1 result согласно Task85 nested-model principle.

Отдельно указать известный Task85 gap:

    Fingerprint V2 содержит почти
    отсутствующее G2-specific coverage.

Task87 не должен самовольно создавать
новые G2 metrics после начала fitting.
Если дополнительные G2 metrics необходимы,
они должны быть preregistered/frozen
до G2 experiment.


======================================================================
46. FREEZE
======================================================================

Если experiment валиден и результат
можно передать Task87, создать:

    TOKEN_GRAMMAR_FROZEN.

Freeze marker должен ссылаться на:

    Task85 freeze;
    calibration freeze;
    model-selection freeze;
    authoritative corpus checksums;
    selected-model checksums;
    results manifest;
    git commit.

Если experiment выполнен корректно,
но frozen evidence не позволяет определить
достаточный/минимальный G1 class:

    TOKEN_GRAMMAR_INCONCLUSIVE.

INCONCLUSIVE является допустимым
научным результатом и не считается failure.


======================================================================
47. VALIDATION
======================================================================

Обязательно:

    authoritative provenance verification;
    Task85 checksum verification;
    split verification;
    calibration-before-VM verification;
    HELDOUT access audit;
    seed ledger verification;
    model artifact checksum verification;
    deterministic regeneration tests;
    result-manifest verification.

Для Go code:

    go build ./...
    go vet ./...
    go test ./...
    go test -race ./...

Всегда:

    git diff --check.
