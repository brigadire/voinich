Нужно реализовать анализатор для поиска кандидатов на парные конструкции типа `begin-end` в корпусе манускрипта Войнича.

Исходная гипотеза: некоторые токены могут открывать и закрывать структурный блок. Между ними может находиться произвольное число других токенов. Мы не предполагаем никакого значения токенов и не считаем найденные пары операторами без дополнительной проверки.

Исходные данные: YAML-словарь, где для каждого токена известны:

* общее число появлений;
* распределение позиции в строке;
* `line_start_count`;
* `line_end_count`;
* полный список токенов, встречающихся непосредственно перед ним;
* полный список токенов, встречающихся непосредственно после него.

Для полноценного поиска дальних `begin-end` зависимостей также использовать исходный линейный корпус с сохранёнными границами строк и страниц. Если его нет в текущем проекте, архитектуру сделать так, чтобы анализ дальних зависимостей подключался отдельным модулем.

Цель первой итерации — найти пары токенов `A, B`, для которых наблюдаются признаки отношения:

`A ... B`

и при этом связь между A и B статистически сильнее случайного совпадения.

Нужно проверить как минимум следующие признаки.

1. Позиционная комплементарность.

Для каждого токена вычислить:

* вероятность появления в начале строки;
* вероятность появления в конце строки;
* среднюю и нормированную позицию в строке.

Искать пары, где A заметно смещён к началу последовательности, а B — к концу.

Это только один из признаков и не должно быть обязательным условием.

2. Направленная дальняя связь.

Для каждого появления A искать ближайшее последующее появление B в пределах:

* той же строки;
* того же абзаца, если границы доступны;
* той же страницы.

Проверять окна расстояний:

`1, 2, 3, 5, 8, 13, 21, 34, 55` токенов,

а также режим `до конца строки` и `до конца страницы`.

Для каждой пары считать:

* число появлений A;
* сколько раз после A встретился B в заданном окне;
* `P(B within window | A)`;
* среднее расстояние A→B;
* медианное расстояние;
* распределение расстояний;
* сколько A осталось без B;
* сколько B встретилось без предшествующего A.

3. Направленность.

Отдельно сравнить:

`A ... B`

и

`B ... A`.

Сильная begin-end пара должна иметь выраженную асимметрию.

Ввести показатель, например:

`directionality = P(B after A) - P(A after B)`

или логарифмическое отношение вероятностей.

4. Статистическая неожиданность.

Частые токены естественным образом часто оказываются рядом.

Поэтому для каждой пары нужно сравнивать наблюдаемую частоту с ожидаемой при независимом распределении.

Использовать как минимум один из методов:

* permutation test;
* z-score относительно случайно перемешанных последовательностей;
* log-likelihood ratio;
* PMI для дальнего контекста.

Предпочтительно permutation test.

Важно: перемешивание должно сохранять границы страниц, а в отдельном режиме — и длины строк. Нельзя просто перемешивать весь корпус глобально.

5. Вложенность.

Отдельно проверить пары на структуры вида:

`A ... A ... B ... B`

и

`A ... B ... A ... B`.

Для настоящих открывающих/закрывающих конструкций первый тип может встречаться чаще второго.

Посчитать частоты четырёх порядков:

`A A B B`
`A B A B`
`A B B A`
`B A A B`

без предположения, какой из них «правильный».

6. Баланс в пределах страницы.

Для каждой пары A/B по каждой странице считать:

`count(A) - count(B)`.

Интересны пары, где эта величина часто близка к нулю или имеет небольшую дисперсию относительно случайных пар токенов сходной частоты.

Не требовать точного равенства.

7. Локальная совместимость.

Использовать уже существующие `word_before` и `word_after`, чтобы исключить тривиальные биграммы.

Если `A B` почти всегда стоят непосредственно рядом, это скорее локальная конструкция, а не begin-end. Такие пары выводить отдельно.

Результат должен быть ранжированным списком кандидатов.

Для каждой пары сохранить примерно такую структуру:

```yaml
begin_candidate: qokedy
end_candidate: shedy

counts:
  begin: 305
  end: 287

position:
  begin_start_probability: 0.41
  begin_end_probability: 0.03
  end_start_probability: 0.04
  end_end_probability: 0.37

distance:
  observations: 214
  mean: 8.3
  median: 6
  histogram:
    1: 4
    2: 9
    3: 11

directionality:
  a_to_b: 0.70
  b_to_a: 0.19
  score: 0.51

page_balance:
  mean_difference: 0.21
  stddev_difference: 0.84

nesting:
  AABB: 31
  ABAB: 7
  ABBA: 4
  BAAB: 3

significance:
  permutation_p: 0.001
  z_score: 4.8

score: 0.87
```

Не использовать один непрозрачный ML-score. Итоговый `score` можно вычислять для сортировки, но все исходные метрики должны сохраняться отдельно.

Нужно сформировать минимум три отчёта:

* `begin_end_candidates.yaml` — полный машинно-читаемый результат;
* `begin_end_top.tsv` — компактная таблица лучших кандидатов;
* `begin_end_report.md` — человекочитаемый отчёт с пояснением наиболее сильных пар и используемых метрик.

В отчёте отдельно показать:

* лучшие пары внутри строки;
* лучшие пары внутри страницы;
* пары с наиболее сильной направленностью;
* пары с наиболее выраженным балансом;
* пары с признаками вложенности.

Не присваивать токенам семантические значения вроде `BEGIN`, `END`, `IF`, `LOOP`. Использовать только нейтральные формулировки: `opening candidate`, `closing candidate`, `paired token`, `directed dependency`.

Особое внимание уделить токенам с `?`: они содержат неразборчивые знаки и должны либо исключаться из основного рейтинга, либо анализироваться отдельным режимом. Конструкции `@NNN;` являются валидными символами транслитерации и не должны удаляться или разбиваться.

Код должен быть детерминированным при заданном random seed, иметь CLI и позволять задавать:

* путь к YAML;
* путь к корпусу;
* максимальное окно;
* число перестановок;
* минимальную частоту токена;
* random seed;
* каталог результатов.

Главная задача первой итерации — не доказать существование begin-end конструкций, а определить, существуют ли в корпусе статистически устойчивые дальние пары токенов, которые разумно исследовать дальше.
