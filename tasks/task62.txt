Task62 — Local Token-Formation Grammar and Generative Validation

Цель

Проверить гипотезу:

    значительная часть необычного fingerprint Voynich может возникать
    из локальных ограничений на образование token forms,

без необходимости отдельно постулировать:

    - сложную последовательную грамматику tokens;
    - homophonic cipher;
    - несколько независимых механизмов для positional specialization,
      low h2 и dense edit neighborhoods.

Task62 должен построить минимальную generative model допустимых
glyph sequences, используя только локальную структуру Voynich tokens,
а затем на независимых данных проверить, возникают ли как следствие
уже известные свойства Tasks 59–61.

Ключевой принцип:

    модель НЕ оптимизируется по Task59/60/61 metrics.

Эти metrics являются только OUT-OF-SAMPLE VALIDATION TARGETS.

НЕ добавлять Stage29.
НЕ изменять Stages 1–28.
НЕ использовать Task52 fingerprint distance как objective.
НЕ подбирать параметры по сходству generated corpus с Voynich.

======================================================================
1. PRIMARY HYPOTHESIS
======================================================================

Проверить:

    LOCAL_TOKEN_FORMATION hypothesis

то есть существование относительно простой локальной модели:

    P(g_i | local glyph context, token position/boundary)

способной объяснить одновременно:

    A. low glyph conditional entropy;
    B. strong positional specialization;
    C. dense edit-distance-1 vocabulary neighborhoods;

без непосредственной оптимизации этих свойств.

Отдельно проверить, может ли такая модель объяснить:

    D. adjacent near-repetition enrichment.

D принципиально отличается от A–C, поскольку требует информации
о последовательности tokens.

======================================================================
2. IMPORTANT NULL INTERPRETATION
======================================================================

Task62 НЕ является:

    decipherment;
    language model;
    cipher reconstruction;
    proof of morphology.

Если local grammar воспроизводит fingerprint, вывод только:

    observed properties могут быть следствием ограниченного
    token-formation mechanism.

======================================================================
3. PRE-REGISTRATION
======================================================================

До генерации validation corpora создать:

    TOKEN_FORMATION_DESIGN.md

    train/validation/test split;
    hyperparameters;
    smoothing;
    stopping rules;
    token-length treatment;
    generation protocol;
    random seeds;
    primary metrics;
    acceptance criteria.

После первого просмотра test results:

    DESIGN_FROZEN

и параметры не менять.

Если модель проваливает validation:

    фиксировать negative result,

а не дообучать её под Voynich fingerprint.

======================================================================
4. FIRST REQUIRED ANALYSIS — LENGTH CONFOUND
======================================================================

Перед generative experiment проверить результат Task61:

    giant edit family:
        h2 ≈ 1.9894

    outside:
        h2 ≈ 2.8050.

Использовать ENTROPY_BY_TOKEN_LENGTH.

Для каждого достаточно представленного L вычислить:

    h2(giant | length=L)
    h2(outside | length=L)

и:

    Δh2(L).

Также выполнить frequency/size-aware aggregation.

Создать:

    EDIT_FAMILY_ENTROPY_LENGTH_CONTROL.tsv

Цель:

    определить, сохраняется ли связь giant edit family ↔ low entropy
    после контроля token length.

======================================================================

Разделить transitions минимум на:

    MEDIAL -> next
    penultimate -> FINAL

Создать:

Цель:

    локализовать источник glyph predictability внутри token.

======================================================================
6. SHARED GLYPH REPRESENTATION
======================================================================

Использовать только:

    internal/evaglyph

из Tasks 58–61.

Не создавать новую EVA interpretation.

Все:

    composites
    uncertain forms
    malformed tokens

обрабатывать по существующим shared rules.

======================================================================
7. DATA SPLIT
======================================================================

Voynich token occurrences разделить на:

    TRAIN
    VALIDATION
    TEST.

Split должен предотвращать очевидную утечку соседних участков текста.

Предпочтительно:

    page/folio-block split

или другой block-level split.

Не использовать random individual-token split как единственный protocol.

Причина:

    соседние Voynich tokens сильно похожи;
    random token split может дать leakage.

======================================================================
8. VOCABULARY LEAKAGE
======================================================================

Отдельно фиксировать:

    seen test token types
    unseen test token types.

Generative evaluation проводить для обоих случаев.

Нельзя считать способность воспроизводить TRAIN vocabulary
доказательством генеративной способности.

======================================================================
9. BASELINE 0 — EMPIRICAL TOKEN SAMPLING
======================================================================

Создать baseline:

    выбирать целый token из TRAIN
    согласно его empirical frequency.

Он идеально сохраняет существующие forms, но:

    не создаёт новые token types.

Это нижний conceptual baseline для генеративности.

======================================================================
10. BASELINE 1 — IID GLYPHS
======================================================================

Генерировать:

    token length ~ empirical TRAIN length distribution

затем:

    glyph_i ~ P_train(g)

независимо.

Это сохраняет:

    glyph frequencies
    token-length distribution

и уничтожает local formation rules.

======================================================================
11. BASELINE 2 — POSITION-CONDITIONED IID
======================================================================

Генерировать glyphs независимо из:

    P(g | INITIAL)
    P(g | MEDIAL)
    P(g | FINAL)

с empirical token-length distribution.

Это непосредственно проверяет:

    достаточно ли одной Task59 positional specialization?

Без glyph-to-glyph transition rules.

======================================================================
12. MODEL A — FIRST-ORDER TOKEN MARKOV
======================================================================

Основная минимальная модель:

    <BOS> -> g1 -> g2 -> ... -> gn -> <EOS>

с:

    P(g_i | g_i-1).

Model обучается только на TRAIN tokens.

Token boundaries обязательны.

Smoothing зафиксировать заранее.

Не использовать Task59/60/61 scores для выбора smoothing.

======================================================================
13. MODEL B — SECOND-ORDER TOKEN MARKOV
======================================================================

Следующая модель:

    P(g_i | g_i-2, g_i-1).

Она допустима только как заранее определённое усложнение Model A.

Сравнение A/B должно показать:

    требуется ли второй порядок для observed token structure.

======================================================================
14. MODEL C — POSITION-AWARE FIRST ORDER
======================================================================

Модель:

    P(g_i | g_i-1, positional_region)

где positional_region определяется формально:

    INITIAL
    MEDIAL
    FINAL

без лингвистических терминов.

Это проверяет комбинацию:

    local transitions
    +
    positional constraints.

======================================================================
15. MODEL COMPLEXITY LIMIT
======================================================================

Не строить:

    neural network
    transformer
    unrestricted n-gram search
    grammar induction with hundreds of fitted rules.

Цель Task62 — MINIMAL explanatory model.

Если простой механизм не работает:

    это важный negative result.

======================================================================
16. TOKEN LENGTH
======================================================================

Основной generation protocol должен брать:

    token length ~ empirical TRAIN distribution.

Отдельный extension может моделировать EOS вероятностно.

Но нельзя позволять модели выигрывать только за счёт копирования
полного empirical token list.

======================================================================
17. GENERATION
======================================================================

Для каждой model family генерировать corpus с тем же числом token
occurrences, что TEST corpus.

Минимум:

    100 independent generated corpora

если computationally дешёво.

Seeds фиксировать.

Generated corpora не должны использовать test data.

======================================================================
18. PRIMARY HELD-OUT LIKELIHOOD
======================================================================

До fingerprint metrics оценить собственно качество модели:

    held-out cross entropy
    perplexity

на TEST tokens.

Это PRIMARY model-quality criterion.

Модель должна сначала предсказывать unseen data,
а не просто выглядеть статистически похожей на Voynich.

======================================================================
19. UNSEEN TOKEN GENERATION
======================================================================

Для generated corpora измерить:

    fraction generated types not present in TRAIN
    fraction generated occurrences belonging to new types.

Сравнить формы новых generated tokens с TEST unseen types.

======================================================================
20. TEST-TYPE COVERAGE
======================================================================

Вычислить:

    fraction of TEST token types generated at least once

и отдельно:

    unseen TEST types generated.

Не требовать высокого exact recovery как основной критерий,
но фиксировать результат.

23. VALIDATION TARGET C — EDIT-FAMILY STRUCTURE

======================================================================
24. CRITICAL NOVEL-TYPE VERSION
======================================================================

Edit graph обязательно анализировать отдельно для:

    all generated types

и:

    generated types NOT PRESENT IN TRAIN.

Это критический test.

Если giant component возникает только потому, что модель повторно
генерирует TRAIN tokens:

    generative explanation NOT CONFIRMED.

======================================================================
25. VALIDATION TARGET D — NEAR-REPETITION
======================================================================

Сгенерированные tokens сначала расположить независимо.

Измерить:

    adjacent d=1 enrichment.

Ожидается, что чистая token-formation model может воспроизвести
vocabulary geometry, но НЕ обязательно sequential enrichment.

Это важное различие.

======================================================================
26. INDEPENDENT-SEQUENCE TEST
======================================================================

Если модели A–C воспроизводят:

    h2

    giant edit family

но НЕ:

    adjacent near-repeat enrichment,

зафиксировать:

    TOKEN_FORMATION_SUFFICIENT_FOR_FORM
    BUT
    SEQUENCE_MECHANISM_REQUIRED.

Это потенциально очень важный результат.

======================================================================
27. OPTIONAL MODEL D — PREVIOUS-TOKEN CONDITIONING
======================================================================

Только если §26 даёт именно такой результат.

Заранее определить простой extension:

    generation of T_i conditioned on limited information from T_i-1.

НЕ использовать identity предыдущего token целиком.

Разрешённые варианты должны быть зафиксированы в DESIGN до test,
например:

    previous final glyph

или:

    previous token length.

Не добавлять feature после просмотра результатов.

======================================================================
28. NO DIRECT EDIT COPYING
======================================================================

Запрещён основной model вида:

    take previous token
    mutate one glyph.

Такой механизм тривиально создаст Task60 result.

Его можно использовать только как POSITIVE CONTROL,
не как explanatory model Task62.

======================================================================
29. POSITIVE CONTROL — COPY/MUTATE
======================================================================

Создать отдельный synthetic positive control:

    with probability p:
        copy previous token and perform one random edit;

    otherwise:
        sample independent token.

Параметр p фиксируется заранее и НЕ подбирается к Voynich.

Цель:

    убедиться, что Task60 validation действительно чувствителен
    к sequential near-copy mechanism.

======================================================================
41. ACCEPTANCE — LOCAL FORMATION
======================================================================

LOCAL_FORMATION_SUPPORTED:

    frozen local model одновременно воспроизводит в held-out generation:

        low h2
        positional specialization
        dense d=1 vocabulary structure

    в пределах заранее определённых intervals/tolerances,

    включая novel generated types.

PARTIAL:

    воспроизводит два из трёх.

NOT_SUPPORTED:

    воспроизводит <=1 либо требует direct copying TRAIN vocabulary.

======================================================================
42. ACCEPTANCE — SEQUENTIAL STRUCTURE
======================================================================

SEQUENCE_INDEPENDENT_SUFFICIENT:

    independent generated tokens также воспроизводят observed
    near-repeat enrichment.

SEPARATE_SEQUENCE_RULE_REQUIRED:

    token-form metrics воспроизводятся,
    adjacent d=1 enrichment — нет.

LOCAL_MODEL_INSUFFICIENT:

    не воспроизводится уже token-form fingerprint.

======================================================================
43. IMPORTANT INTERPRETATION
======================================================================

Если получено:

    LOCAL_FORMATION_SUPPORTED
    +
    SEPARATE_SEQUENCE_RULE_REQUIRED,

это НЕ означает "мы нашли грамматику Voynich".

Это означает только:

    несколько ранее считавшихся независимыми аномалиями могут иметь
    общий источник — локальные constraints образования tokens,

    тогда как adjacency enrichment требует дополнительного объяснения.

44. CRYPTOGRAPHIC INTERPRETATION
======================================================================

DEFINITION OF DONE
======================================================================

Task62 завершён, когда:

1. giant-family h2 contrast проверен с контролем длины;

2. frequency confound giant family проверен;

3. positional source of entropy локализован;

4. train/validation/test разделены без token-level leakage;

5. реализованы IID и positional-IID baselines;

6. реализованы Markov-1, Markov-2 и positional Markov-1;

7. model selection выполнен только на TRAIN/VALIDATION;

8. DESIGN заморожен до TEST;

9. frozen model один раз проверена на TEST;

10. generated corpora проверены authoritative Task59–61 metrics;

11. отдельно проверены novel generated token types;

12. определено, возникает ли giant d=1 component из local grammar;

13. определено, возникает ли adjacent near-repeat enrichment
    без sequential mechanism;

14. natural-language controls проходят тот же protocol;

15. выполнены ablations;

16. результат классифицирован:
        LOCAL_FORMATION_SUPPORTED /
        PARTIAL /
        NOT_SUPPORTED;

17. sequential result классифицирован:
        SEQUENCE_INDEPENDENT_SUFFICIENT /
        SEPARATE_SEQUENCE_RULE_REQUIRED /
        LOCAL_MODEL_INSUFFICIENT;

18. никаких выводов о значении glyphs, языке или дешифровке не сделано;

19. Stages 1–28 не изменены.
