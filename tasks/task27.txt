# Task: repository-wide performance and architecture refactoring

Провести системный performance-refactoring всего аналитического pipeline
репозитория, используя успешную оптимизацию `transition-network-validate`
как эталон подхода.

## Контекст

Репозиторий содержит большое число аналитических CLI, многие из которых
выполняют permutation/bootstrap/random-baseline/cross-validation расчёты.
Некоторые этапы полного pipeline занимают от нескольких часов до ~15 часов.

Недавнее профилирование `transition-network-validate` обнаружило, что основная
причина высокой стоимости была не в статистическом алгоритме как таковом,
а в реализации hot path:

- повторное создание больших `map[string]...` и `map[EdgeKey]...`;
- string hashing в тысячах permutation replicates;
- повторный расчёт invariant quantities;
- огромный allocation churn и GC;
- вычисление промежуточных результатов, которые конкретной стадии не нужны.

После введения compiled dense workspace:

- wall-clock полного 1000 + 10000 permutation run уменьшился до ~84 секунд;
- результаты остались идентичными reference implementation;
- statistical methodology не изменилась.

Нужно проверить, насколько те же проблемы распространены по всему repository,
и создать общую эффективную вычислительную архитектуру там, где это оправдано.

# Главное ограничение

Это PERFORMANCE/ARCHITECTURE REFACTORING.

НЕЛЬЗЯ изменять:

- статистические гипотезы;
- формулы метрик;
- null models;
- permutation semantics;
- bootstrap semantics;
- random-baseline semantics;
- eligibility rules;
- thresholds;
- search spaces;
- frozen candidate sets;
- multiple-comparison correction;
- FDR procedures;
- seed semantics;
- physical-block semantics;
- line/page boundary semantics;
- metadata conditioning;
- train/test split semantics;
- leakage protection;
- checkpoint semantics;
- существующие output schemas;
- имена/смысл output fields;
- deterministic ordering.

Оптимизированный код должен вычислять тот же эксперимент, а не
математически похожий эксперимент.

Нельзя уменьшать количество permutations, samples, folds, windows или
candidate pairs ради ускорения production/default runs.

# Phase 2 — common immutable corpus representation

Проверить возможность введения общего внутреннего representation, например:

    internal/corpusmodel

или другого подходящего package.

Цель — после parsing корпуса иметь canonical immutable representation:

    token string <-> TokenID integer

и плотные структуры для:

- token sequence;
- line boundaries;
- physical blocks;
- metadata labels;
- token counts;
- block token counts;
- transition indices;

где это действительно переиспользуется несколькими анализаторами.

Предпочтительный тип TokenID выбрать на основании реального vocabulary size.
Не hardcode uint16/int32 без проверки диапазона.

String tokens должны сохраняться на I/O/reporting boundary.
Внутренние repeated numerical calculations по возможности должны работать
с integer IDs.

ВАЖНО:

не делать massive rewrite всех packages только ради единого abstraction.
Shared representation вводить только там, где оно уменьшает реальную
стоимость или дублирование.

# Phase 5 — optimize hot paths

Использовать следующие техники только после подтверждения profiler:

## A. Compile strings to IDs

В repeated numerical hot loops заменить string-keyed structures на dense
integer-indexed representations там, где это корректно.

## B. Hoist invariants

Вынести за permutation/bootstrap/fold loops всё, что не зависит от replicate.

Например:

- baseline probabilities;
- opportunity counts;
- static masks;
- eligibility;
- block geometry;
- candidate indexing;
- constant normalization factors;
- immutable marginal distributions.

Но внимательно проверить: quantity действительно должно быть invariant
относительно конкретного null model.

## C. Reusable workspace

Для repeated replicates использовать заранее выделенные:

- slices;
- matrices;
- counters;
- temporary vectors;
- scratch buffers.

Избегать повторного `make()` больших структур.

## D. Sparse reset / dirty list

Если dense array значительно больше реально изменяемой части, использовать
dirty indices/generation counters вместо полного memset, если benchmark
подтверждает выигрыш.

## E. Avoid unnecessary outputs

Если permutation stage требует только scalar statistics, не строить profiles,
maps или intermediate structures, которые затем отбрасываются.

Использовать explicit computation modes вместо скрытого изменения поведения.

## F. Preallocation

Использовать известные upper bounds для slice/map capacity.

## G. Avoid repeated parsing

Один CLI не должен повторно читать/парсить один и тот же immutable input без
необходимости.

# Phase 6 — concurrency audit

ТОЛЬКО после устранения allocation/hash/recomputation bottlenecks проверить,
есть ли смысл распараллелить independent replicates.

Не добавлять concurrency автоматически.

Если она добавляется:

- default results должны оставаться deterministic;
- одинаковый seed должен давать одинаковые outputs независимо от scheduling;
- RNG stream каждого replicate должен определяться его index, а не порядком
  выполнения goroutines;
- reduction order floating-point statistics должен быть deterministic;
- checkpoint/resume должен давать тот же результат, что uninterrupted run;
- race detector должен быть чистым.

Если последовательная оптимизация уже даёт приемлемое время, предпочесть
простую последовательную реализацию.

# Phase 7 — correctness oracle

КРИТИЧЕСКОЕ ТРЕБОВАНИЕ.

Перед заменой каждого hot path сохранить reference implementation или создать
эквивалентный test oracle.

Для каждой оптимизации сравнивать old vs new на synthetic fixtures.

Требовать:

- integer/count outputs: exact equality;
- categorical decisions: exact equality;
- RNG-dependent results: exact equality при сохранении iteration semantics;
- floating point: exact equality, где возможно;
- если изменился только порядок суммирования — tolerance не хуже 1e-12 или
  обоснованный более строгий package-specific tolerance.

Отдельно проверять edge cases:

- empty block;
- one-token block;
- absent candidate;
- zero opportunities;
- rare tokens;
- unknown metadata;
- missing transition;
- all-zero vector;
- singleton class;
- boundary token;
- candidate absent from a replicate.

Никогда не превращать "absence" в числовой zero, если старый algorithm
различал эти состояния.

# Execution strategy

НЕ выполнять giant rewrite одним commit.

Работать поэтапно:

1. inventory;
2. profiling;
3. определить top bottlenecks;
4. оптимизировать один analyzer;
5. доказать equivalence;
6. benchmark;
7. только затем переходить к следующему.

Приоритет выбирать по приблизительной величине:

    expected total saved pipeline runtime

а не по простоте изменения кода.

После первых 3–5 analyzer optimizations повторно измерить полный pipeline:
bottleneck может переместиться.

---

# Scientific invariance rule

Главный критерий успешности:

    same experiment + same inputs + same seed
        => same scientific result

Performance improvement не является основанием для изменения statistical
experiment.

Если оптимизация требует изменения experiment semantics — НЕ выполнять её.
Зафиксировать возможность в отчёте отдельно как потенциальную будущую
методологическую работу.

# Initial reference

Использовать оптимизацию `internal/transitionnetwork/permworkspace.go` как
пример успешного pattern:

    strings/maps in hot path
        ↓
    compiled integer representation
        ↓
    precomputed invariants
        ↓
    reusable buffers
        ↓
    specialized computation mode
        ↓
    reference-vs-optimized tests

Но не предполагать заранее, что этот pattern оптимален для каждого analyzer.
Profiler является источником истины.
