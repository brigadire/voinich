Task38 — Extend pipeline-orchestrate for generic corpora

Цель

Расширить существующий `pipeline-orchestrate`, созданный для Voynich/IVTFF, чтобы он мог запускать тот же аналитический pipeline на заранее подготовленных generic token corpora, например:

    data_test/pg2097-2.txt

При этом существующий Voynich workflow и frozen `Voynich Baseline v1` должны остаться полностью неизменными и byte-compatible.

Это изменение orchestration/input layer. НЕ менять научные алгоритмы, statistical parameters, tokenization, RNG, thresholds, windows или формулы анализаторов.

1. Audit

Перед изменениями определить:

- какие из 27 stages действительно требуют исходный IVTFF;
- какие требуют metadata, полученную из IVTFF;
- какие работают исключительно с frozen token corpus;
- dependency chain между этими стадиями.

Зафиксировать результат краткой таблицей:

    stage | corpus-only | IVTFF-required | metadata-required | generic-applicable

Не считать stage Voynich-specific только по названию. Проверить фактические inputs.

2. Два режима orchestrator

Сохранить существующий режим:

    Voynich/IVTFF mode:
        -ivtff data/ZL3b-n.txt
        -corpus data_work/ZL3b-x7.txt

и добавить generic corpus mode.

Предпочтительный CLI:

    bin/pipeline-orchestrate manifest \
        -experiment-dir experiments/doyle-sign-four-v1 \
        -corpus data_test/pg2097-2.txt \
        -generic-corpus \
        ...

Название флага можно изменить, если существующая архитектура подсказывает более естественный вариант.

В generic mode:

- `-corpus` является authoritative frozen input;
- IVTFF не требуется;
- НЕ запускать `ivtt -x7`;
- НЕ использовать Voynich IVTFF или metadata как fallback;
- corpus SHA256 обязательно фиксируется в manifest.

3. Manifest

Расширить manifest так, чтобы тип input был однозначен.

Например:

    input_mode: "generic"
    corpus:
        path: data_test/pg2097-2.txt
        sha256: ...
    ivtff: null

Для старого режима:

    input_mode: "ivtff"
    corpus: ...
    ivtff:
        path: ...
        sha256: ...

Сохранять backward compatibility с существующим `experiments/voynich-v1/manifest.json`.

НЕ переписывать frozen baseline.

4. Stage selection

Generic mode должен запускать все стадии, которые научно и технически применимы без IVTFF/Voynich metadata.

IVTFF/metadata-dependent stages должны:

- либо отсутствовать из execution plan;
- либо иметь явный статус `NOT_APPLICABLE`.

Предпочтительно сохранить полный stage inventory в manifest/report и явно записывать:

    status: NOT_APPLICABLE
    reason: requires IVTFF metadata

чтобы отсутствие результата нельзя было принять за сбой pipeline.

Не создавать фиктивные Currier/hand/folio metadata для generic corpora.

5. Dependency handling

Если corpus-generic stage зависит от artifact, который сейчас создаётся Voynich-specific stage, проверить, является ли dependency действительно научной или только исторической особенностью pipeline.

Если generic equivalent можно получить без изменения алгоритма — использовать его.

Если нельзя — stage становится NOT_APPLICABLE.

Не изобретать synthetic metadata только ради прохождения dependency graph.

6. Distributed execution

Существующий remote executor должен продолжить работать для generic corpora там, где соответствующая стадия generic-applicable.

Сохранить без изменений:

- mTLS;
- JobID semantics;
- deterministic replicate seeds;
- checkpoint/resume;
- deterministic reduction;
- worker elasticity;
- retry semantics.

Worker count/identity не должны влиять на scientific outputs.

7. Freeze/resume/status

Generic experiments должны полностью поддерживать существующие:

    manifest
    run
    status
    freeze
    verify

Resume должен учитывать NOT_APPLICABLE stages как завершённые и не пытаться запускать их повторно.

Frozen generic experiment должен содержать:

- immutable manifest;
- run-state;
- stage logs;
- outputs;
- checksums;
- REPORT.md;
- FROZEN marker.

8. Reports

REPORT.md должен явно указывать:

    Input mode: generic corpus
    Corpus: ...
    Corpus SHA256: ...
    Token count: ...

и отдельный список:

    Not applicable stages:
      ...
      reason: ...

Никаких упоминаний Voynich/IVTFF как input generic experiment.

9. Tests

Добавить минимум:

A. Existing Voynich manifest regression
   Старый invocation создаёт семантически идентичный execution plan.

B. Generic manifest
   Создаётся без IVTFF.

C. No contamination
   Generic experiment нигде не читает:
       data/ZL3b-n.txt
       data_work/ZL3b-x7.txt
   если они не были явно переданы.

D. Stage dependency
   Corpus-only stages запускаются.
   IVTFF/metadata stages корректно становятся NOT_APPLICABLE.

E. Resume
   Generic interrupted run корректно продолжается.

F. Freeze/verify
   Generic run можно заморозить и проверить.

G. Distributed oracle
   На небольшом generic fixture local/process и remote execution дают byte-for-byte identical scientific outputs для distributed-applicable stage.

10. Acceptance run

После реализации НЕ запускать полный production analysis.

Выполнить небольшой smoke-run на:

    data_test/pg2097-2.txt

с уменьшенными computational parameters только для проверки orchestration.

Подтвердить:

- IVTFF не читается;
- Voynich metadata не читается;
- execution plan корректен;
- applicable stages выполняются;
- остальные явно NOT_APPLICABLE;
- remote executor работает;
- resume работает;
- freeze/verify работает.

Smoke-run не считать научным результатом и не добавлять в comparative baseline.

11. Backward compatibility

Критическое требование:

    experiments/voynich-v1/

не изменять вообще.

Все 340 frozen checksums должны остаться валидными.

Существующий Voynich production invocation должен продолжать работать без новых обязательных flags.

12. Не делать

НЕ:

- менять анализаторы без необходимости для generic orchestration;
- менять fixed window sizes;
- менять thresholds/min-counts;
- делать adaptive parameters по corpus size;
- менять tokenization;
- создавать synthetic Currier/hand metadata;
- менять RNG;
- менять scientific formulas;
- менять frozen Voynich Baseline v1;
- начинать cross-corpus classification/feature analysis.

Deliverables

- изменения `pipeline-orchestrate`;
- tests;
- `GENERIC_CORPUS_ORCHESTRATION.md` с audit таблицей 27 stages и описанием generic execution;
- при необходимости обновление `DISTRIBUTED_EXECUTION_OPERATIONS.md`.

Validation:

    go build ./...
    go vet ./...
    go test ./...
    git diff --check

Definition of Done

`pipeline-orchestrate` принимает заранее подготовленный corpus произвольного размера без IVTFF, строит корректный dependency-aware execution plan, запускает все применимые corpus-generic stages, явно маркирует остальные NOT_APPLICABLE, поддерживает distributed execution/resume/freeze/verify и никогда не подмешивает Voynich IVTFF/metadata.

Существующий Voynich workflow и frozen Voynich Baseline v1 остаются byte-for-byte неизменными.
