Task47 — Distributed execution for Stage 5 begin-end-analyze

Цель

Добавить поддержку существующей distributed execution infrastructure
к Stage 5:

    begin-end-analyze

Причина:

На реальном generic corpus:

    experiments/astafiev-1000-culinar-receipt-v1

Stage 5 выполнялся:

    14m52s

Это уже существенная доля полного pipeline runtime.

Основное требование:

Ускорить begin-end-analyze распределённым выполнением без какого-либо
изменения scientific semantics, RNG semantics, statistical formulas,
candidate selection, thresholds или output schemas.

======================================================================
1. СНАЧАЛА PROFILE / PARALLELISM AUDIT
======================================================================

До изменения production code выполнить profiling текущего Stage 5 на
реальном корпусе Astafiev.

Снять:

    CPU profile
    alloc_space profile
    live heap / RSS
    wall-time breakdown

Определить, какие части дают основную стоимость.

Особенно проверить циклы по:

- token pairs;
- begin/end candidates;
- distance calculations;
- permutations/random baselines;
- blocks;
- pattern classes;
- AABB / ABAB / ABBA / BAAB tests;
- directionality/complementarity calculations.

Создать таблицу:

    operation
    wall/CPU share
    natural work unit
    independent?
    RNG dependency?
    reduction dependency?
    distributable?

Не начинать distribution до определения независимой work unit.

======================================================================
2. NATURAL WORK UNIT
======================================================================

Предпочтительно найти максимально крупную независимую единицу:

    candidate pair
    permutation replicate
    block
    candidate batch

или другую единицу, подтверждённую фактической архитектурой.

Не распределять микроскопические операции.

Work unit должна быть достаточно крупной, чтобы network/RPC overhead
оставался мал по сравнению с computation time.

Если основной cost состоит из огромного числа candidate pairs,
предпочесть deterministic batches диапазонов candidate IDs вместо одного
remote job на каждую пару.

Например:

    job 0: candidates [0, 999]
    job 1: candidates [1000, 1999]
    ...

Точный размер batch определить профилированием/benchmark.

======================================================================
3. DETERMINISTIC INDEXING
======================================================================

Все candidates/work units должны получить deterministic stable IDs.

Нельзя зависеть от:

    Go map iteration order
    goroutine scheduling
    worker completion order
    host identity

При одинаковом corpus + parameters + seed logical job decomposition
должна быть одинаковой.

======================================================================
4. RNG AUDIT
======================================================================

Если begin-end-analyze использует permutations/random baselines:

проверить существующий RNG flow.

Если RNG сейчас последовательный/global, определить, можно ли безопасно
перейти к independent replicate seed:

    seed = F(baseSeed, logicalWorkID, replicateIndex)

ТОЛЬКО если это не меняет существующий scientific result.

Предпочтительный вариант — сохранить существующий RNG stream и доказать,
что work units уже независимы.

Если distributed execution невозможно без изменения RNG semantics:

НЕ менять RNG молча.

Остановить эту часть и документировать ограничение.

Byte-for-byte scientific identity с local oracle является обязательной.

======================================================================
5. EXISTING REMOTE EXECUTOR
======================================================================

Не создавать новую distributed framework.

Использовать существующую инфраструктуру Task31–35 / Task44:

- coordinator;
- workers;
- mTLS;
- deterministic JobID;
- lease;
- timeout;
- retry/reassignment;
- checkpoint/resume;
- worker elasticity;
- deterministic reduction.

По возможности вынести/использовать общий executor API вместо копирования
кода из conditional-regime или других distributed stages.

======================================================================
6. CLI
======================================================================

begin-end-analyze должен получить стандартный executor interface:

    -executor goroutine|process|remote
    -workers N

для remote:

    -remote-listen
    -tls-cert
    -tls-key
    -client-ca
    -remote-timeout
    -remote-retries

и checkpoint/resume parameters, если они предусмотрены общей
инфраструктурой.

Default execution mode должен сохранять существующее поведение.

======================================================================
7. LOCAL EXECUTION
======================================================================

После рефакторинга один scientific implementation должен использоваться
для:

    goroutine
    process
    remote

Не создавать отдельную "remote scientific implementation".

Executor меняет только способ выполнения work units.

======================================================================
8. DETERMINISTIC REDUCTION
======================================================================

Remote workers могут завершаться в произвольном порядке.

Scientific aggregation НЕ должна выполняться в arrival order.

Результаты сначала восстановить в canonical logical order:

    workID 0
    workID 1
    ...
    workID N

и только затем выполнять floating-point/statistical reduction.

Это необходимо для byte-for-byte identity.

Не заменять это epsilon/tolerance equivalence.

======================================================================
9. FAILURE / RETRY
======================================================================

Проверить:

- worker disappears during job;
- RPC timeout;
- duplicate completion;
- retry;
- coordinator restart/resume, если поддерживается;
- worker joins during run.

Повторное выполнение одного logical JobID не должно менять результат.

Duplicate result должен безопасно игнорироваться.

======================================================================
10. ORCHESTRATOR INTEGRATION
======================================================================

После доказанной distributed implementation:

Stage 5 в pipeline-orchestrate должен получить:

    Executor=true

или эквивалент существующей архитектуры.

При:

    pipeline-orchestrate manifest \
        ... \
        -executor remote \
        -remote-listen ... \
        ...

Stage 5 должен реально получать:

    -executor remote
    -remote-listen
    -tls-cert
    -tls-key
    -client-ca
    ...

Проверить generated manifest непосредственно тестом.

Не считать наличие executor=remote на уровне experiment достаточным:
Stage 5 command line должен действительно содержать remote parameters.

======================================================================
11. CORRECTNESS ORACLE
======================================================================

Использовать существующий begin-end-analyze как reference implementation.

На одном и том же corpus/parameters/seed выполнить:

A. original/local reference
B. new goroutine
C. process
D. remote 1 worker
E. remote multiple workers
F. interrupted remote + resume

Все scientific output files должны быть SHA256-identical.

Если implementation refactoring меняет float accumulation order,
исправить deterministic order, а не принимать approximate equivalence.

======================================================================

Измерить:

    local baseline
    remote 1 worker
    remote 2 workers
    remote 5 workers
    remote 10 workers

Для каждого:

    total wall time
    distributed computation time
    coordinator CPU
    coordinator RSS
    worker CPU
    worker RSS
    jobs completed
    average job duration
    coordinator/network overhead
    speedup
    parallel efficiency

Не запускать остальные 26 pipeline stages.

======================================================================
13. GRANULARITY STUDY
======================================================================

Если candidate count велик, отдельно проверить несколько batch sizes.

Например:

    32
    128
    512
    2048 candidates/job

или значения, соответствующие реальному профилю.

Цель — избежать:

    слишком мелких RPC jobs

и одновременно сохранить нормальный load balancing.

Выбранный default должен быть обоснован измерениями.

======================================================================
14. PERFORMANCE TARGET
======================================================================

Не устанавливать искусственный обязательный speedup.

Но при исходных:

    14m52s

distribution считается практически оправданной, если production workload
демонстрирует существенное масштабирование.

Особенно интересен результат на 5 и 10 workers.

Если speedup оказывается слабым из-за serial fraction, явно определить
serial bottleneck и не скрывать отрицательный результат.

DEFINITION OF DONE
======================================================================

Task47 завершён, когда begin-end-analyze может выполняться через:

    -executor remote

с существующими workers/mTLS infrastructure, pipeline-orchestrate
действительно передаёт Stage 5 remote configuration, а scientific outputs
при local/process/remote execution остаются byte-for-byte identical.

На реальном Astafiev Stage 5 workload выполнен scaling study относительно
зафиксированного baseline:

    14m52s

и документировано фактическое ускорение либо доказанная причина отсутствия
масштабирования.
