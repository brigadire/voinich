Task55 — Frequency-Dependent Homophonic Corpus Transformation

Цель

Расширить corpus-transform новым режимом homophonic substitution, в котором
число доступных гомофонов зависит от частоты plaintext token.

Мотивация

Эксперименты с существующими моделями:

    uniform
    weighted / triangular-v1

показали устойчивую картину:

1. увеличение H последовательно ослабляет transition structure и при H≈8
   приводит её очень близко к Voynich;

2. relation family имеет optimum примерно около H≈4;

3. sequence organization Voynich этими моделями не воспроизводится;

4. vocabulary-growth также не воспроизводится полностью:
   Heaps beta Voynich близок примерно к H4, но Voynich имеет существенно
   более высокую долю hapax;

5. увеличение глобального H одновременно воздействует на частые и редкие
   plaintext types и слишком сильно увеличивает vocabulary.

Следующая проверяемая гипотеза:

    исторически правдоподобная homophonic substitution могла назначать
    больше cipher symbols частым plaintext units и меньше — редким.

ВАЖНО:

    НЕ проектировать функцию так, чтобы она специально приближала Doyle
    к уже известным метрикам Voynich.

======================================================================
1. НОВАЯ МОДЕЛЬ
======================================================================

Добавить новый homophonic model:

    frequency

Пример CLI:

    corpus-transform \
        -corpus INPUT \
        -method homophonic \
        -homophone-model frequency \
        -homophones-max 8 \
        -homophone-selection weighted \
        -seed 1 \
        -output OUTPUT

Точные имена flags согласовать с существующим CLI Task46.

Не ломать существующие:

    uniform
    weighted / triangular-v1

и существующие manifests.

======================================================================
2. ОСНОВНОЙ ПРИНЦИП
======================================================================

Для каждого plaintext token t вычисляется:

    f(t) = raw occurrence count

и определяется:

    H(t) = число доступных homophones для t.

Обязательные свойства:

    H(t) >= 1
    H(t) <= Hmax

и monotonicity:

    f(a) > f(b)

не должно приводить к:

    H(a) < H(b).

То есть более частый plaintext token никогда не получает меньше
гомофонов, чем более редкий.

======================================================================
3. НЕ ПОДБИРАТЬ ФОРМУЛУ ПО VOYNICH
======================================================================

До любых новых Voynich comparisons создать документ:

    FREQUENCY_HOMOPHONE_MODEL.md

В нём заранее зафиксировать математическое определение H(f).

После фиксации модели НЕ менять формулу по результатам Doyle→Voynich
comparison.

Если впоследствии потребуется другая модель — это должна быть новая
version/model, а не изменение frequency-v1.

======================================================================
4. FREQUENCY-V1
======================================================================

Выбрать простую интерпретируемую функцию.

Предпочтительно использовать frequency ranks/quantiles, а не абсолютные
частоты, чтобы модель переносилась между корпусами разного размера.

Например допустима модель вида:

    hapax / very rare      -> H=1
    low-frequency          -> H=2
    medium-frequency       -> H=3...
    highest-frequency      -> H=Hmax

НО:

конкретные границы должны быть определены независимо от Voynich.

Не использовать значения вроде:

    "граница выбрана потому, что при ней Doyle имеет V≈8244".

======================================================================
5. ПРЕДПОЧТИТЕЛЬНО ИСТОРИЧЕСКИ ИНТЕРПРЕТИРУЕМАЯ МОДЕЛЬ
======================================================================

При выборе frequency-v1 ориентироваться на общий принцип классических
гомофонических шифров:

    наиболее частые plaintext units получают больше cipher alternatives,
    чтобы сгладить frequency distribution.

Не требуется моделировать конкретный исторический шифр.

Но функция должна иметь понятное криптографическое объяснение, а не быть
произвольной математической кривой.

======================================================================
6. ДВА НЕЗАВИСИМЫХ МЕХАНИЗМА
======================================================================

Не смешивать:

A. allocation:

    сколько homophones получает plaintext token:

        H(t)

B. selection:

    как выбирается один из H(t) при каждом occurrence.

Существующий Task46 уже имеет selection modes:

    uniform
    weighted / triangular-v1

Frequency model должен управлять только allocation.

По возможности разрешить комбинации:

    frequency + uniform selection
    frequency + weighted selection

Это позволит отдельно исследовать:

    allocation effect

и:

    selection-probability effect.

======================================================================
7. DETERMINISM
======================================================================

При одинаковых:

    corpus
    model
    parameters
    selection
    seed

output должен быть byte-for-byte identical.

Сохранить существующие гарантии Task46.

======================================================================
8. TOKEN MULTISET SEMANTICS
======================================================================

Transformation должна сохранять:

    total token count N.

Каждый plaintext occurrence заменяется ровно одним cipher token.

Не добавлять и не удалять occurrences.

======================================================================
9. TOKEN NAMING
======================================================================

Использовать существующую схему именования homophonic tokens Task46.

Новые cipher token identities должны быть:

    deterministic
    collision-safe
    reversible до plaintext type

в той мере, в какой это уже обеспечивает Task46.

Не создавать отдельный несовместимый формат.

12. MODEL DIAGNOSTICS
======================================================================

До scientific pipeline вывести:

    plaintext types
    cipher types actually observed

    allocated homophones total
    actually observed homophones

    H distribution by plaintext types
    H distribution weighted by occurrences

    hapax plaintext types with H>1

Последнее особенно важно.

Для frequency-v1 ожидается, что большинство/все hapax plaintext types
получат H=1, если это следует из заранее определённой модели.

Не вводить это правило специально ради Voynich после эксперимента.

======================================================================
13. UNIT TESTS
======================================================================

Добавить тесты:

A. Monotonicity

    frequency(a) > frequency(b)
        =>
    H(a) >= H(b)

B. Bounds

    1 <= H(t) <= Hmax

C. Determinism

    same seed -> identical output

D. Seed sensitivity

    different seed изменяет selection там, где это допустимо.

E. N invariant

    N(output) == N(input)

F. Rare token behavior

    проверить ожидаемое allocation frequency-v1.

G. Compatibility

    старые uniform/weighted Task46 fixtures остаются byte-identical.

======================================================================
14. MODEL CALIBRATION — НЕ SCIENTIFIC FIT
======================================================================

До запуска полного pipeline проверить frequency-v1 на Doyle только как
mechanical sanity test.

Получить:

    N
    V
    hapax
    allocation distribution

Но НЕ сравнивать с Voynich для изменения параметров модели.

Если модель математически ведёт себя согласно specification — freeze
frequency-v1.
