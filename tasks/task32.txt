Task32 — Deterministic Local Multi-Process Executor

Goal

Extend the JobID → JobResult architecture proven by Task31 across a local process boundary while preserving exact scientific behavior, RNG semantics, canonical reduction, checkpoint compatibility and byte-for-byte output.

No remote/network workers in this task.

Primary invariant

sequential/reference output == Task31 goroutine output == Task32 multi-process output

for identical corpus, parameters and seed.

Phase 1 — Freeze Task31 oracle

Run the established representative workload, save SHA256 for every output and record exact parameters/seed/worker count.

Phase 2 — Process-safe protocol

Define a versioned local job/result protocol around the Task31 contract.

Requirements:
- deterministic JobID;
- protocol version;
- explicit input/config identity;
- seed derivation remains in shared scientific code;
- no PID/time/hostname/completion-order dependence;
- malformed/incompatible messages fail explicitly.

Prefer a simple standard-library-compatible representation unless measurement disproves it.

Phase 3 — One scientific implementation

Subprocess workers must call the same internal scientific implementation as Task31.

Do not copy/reimplement formulas or create separate process-specific scientific logic.

Phase 4 — Bounded process executor

Provide selectable execution backends, conceptually:

-executor goroutine|process
-workers N

Requirements:
- maximum N active worker processes;
- deterministic job identity;
- arbitrary completion order;
- canonical indexed reduction in coordinator;
- clean child shutdown;
- protocol-safe stdout/stderr handling;
- cancellation on fatal failure;
- no orphan/zombie workers;
- diagnostics identify failed JobID.

Measure whether persistent worker processes are preferable to process-per-replicate and choose based on evidence.

Phase 5 — Input strategy

Compare:
A. serialize full input;
B. workers load immutable input from files;
C. coordinator prepares reusable immutable artifacts referenced by workers.

Choose the smallest reliable design. Measure startup cost, transferred bytes, duplicated memory and repeated parsing/precomputation.

Do not add complex shared memory without profiling evidence.

Phase 6 — Retry/checkpoint/idempotency

Required:
- crash leaves job incomplete;
- retry uses identical scientific input/RNG;
- duplicate completed result cannot count twice;
- coordinator restart resumes;
- worker count may change on resume;
- backend may change on resume where safe.

Explicitly test process→goroutine or goroutine→process resume if the checkpoint model permits it.

Phase 7 — Bit-for-bit matrix

Validate:
1. Task31 workers=1 oracle;
2. goroutine workers>1;
3. process workers=1;
4. process workers>1;
5. interrupted process + resume;
6. resume with different worker count;
7. cross-backend resume where supported.

All scientific outputs must have identical SHA256.

Phase 8 — Benchmark

Benchmark goroutine and process executors at 1/2/4/8 workers, plus 12 where hardware permits.

Report wall time, speedup, efficiency, coordinator CPU, worker CPU if practical, coordinator/worker/total RSS, startup overhead, IPC/serialization overhead and output identity.

The goal is to quantify the isolation/remote-readiness cost, not force processes to beat goroutines.

Phase 9 — Failure tests

Test worker exit, malformed result, duplicate result, wrong/stale JobID, protocol-version mismatch, coordinator cancellation and retry.

Successful retry must reproduce the oracle exactly.

Phase 10 — Task33 boundary

Document the exact small executor boundary that can later become remote transport, conceptually Submit(Job)/Receive(JobResult).

Do not implement sockets, HTTP, RPC, queues or remote discovery.

Documentation

Update DISTRIBUTED_EXECUTION_IMPLEMENTATION.md and, as appropriate, DISTRIBUTED_EXECUTION_AUDIT.md, PERFORMANCE_AUDIT.md and PERFORMANCE_REFACTOR_REPORT.md.

Constraints

- local machine only;
- no network/remote workers;
- no Kubernetes/Redis/Kafka/RabbitMQ/etc.;
- no scientific/statistical/RNG/reduction changes;
- reuse Task31 implementation;
- byte-for-byte compatibility mandatory;
- no unrelated optimization.

Validation

go build ./...
go vet ./...
go test ./...
go test -race ./internal/conditionalregime
git diff --check

Definition of Done

Task32 is complete when conditionalregime has a bounded local process executor; process and goroutine workers use the same scientific implementation; outputs are byte-identical; retry/resume/duplicate protection are deterministic; failures cannot corrupt the experiment; performance/memory/IPC measurements exist; and the executor boundary is ready for Task33.
