Task54 — Controlled Inverse-Transposition Search and Validation Framework

Цель

Создать отдельный экспериментальный инструмент для проверки гипотезы:

    необычная последовательная структура Voynich может быть следствием
    транспозиционного преобразования исходной последовательности.

Инструмент должен искать простые inverse-transposition transformations,
которые восстанавливают признаки естественной последовательной структуры.

Это НЕ дешифратор Voynich.

Это инструмент проверки ограниченного класса криптографических гипотез.

======================================================================
1. ОСНОВНАЯ МОДЕЛЬ
======================================================================

Forward model:

    natural corpus C
        |
        T(theta)
        |
        transformed corpus C'

Inverse problem:

    C'
        |
        search T^-1(theta)
        |
        candidate reconstruction C*

Проверяем:

    восстановились ли заранее определённые structural properties.

======================================================================
2. СНАЧАЛА VALIDATION НА SYNTHETIC CONTROLS
======================================================================

До применения к Voynich инструмент обязан пройти controls.

Минимально:

    Doyle -> T2
    Doyle -> T4
    Doyle -> T8

и желательно другие natural corpora.

Search получает только transformed corpus.

Он НЕ получает original corpus как optimization target.

После поиска original используется исключительно как oracle validation.

======================================================================
3. НЕ ОПТИМИЗИРОВАТЬ СХОДСТВО С DOYLE
======================================================================

Запрещён objective:

    minimize distance(candidate, Doyle)

или:

    maximize natural-language likelihood

на первом этапе.

Это практически гарантирует overfitting.

Objective должен основываться на structural metrics, которые forward
transposition experiments заранее показали чувствительными к
transposition.

======================================================================
4. DIAGNOSTIC METRIC AUDIT
======================================================================

До реализации search objective создать:

    INVERSE_TRANSPOSITION_METRIC_AUDIT.md

На основе:

    Doyle original
    T2/T4/T8 controls
    Voynich controls

классифицировать metrics:

    transposition-sensitive
    transposition-invariant
    weakly sensitive
    unstable
    unsuitable for optimization.

Objective определить ДО запуска поиска на Voynich.

======================================================================
5. ПЕРВЫЙ КЛАСС TRANSFORMATIONS
======================================================================

Начать только с rectangular columnar transposition, совместимой с
corpus-transform Task46.

Параметры минимум:

    width

и заранее определённые orientations/read orders.

Не начинать с произвольных permutations.

Пример initial search space:

    width = 2..16

или другой небольшой заранее зафиксированный диапазон после forward
calibration.

======================================================================
6. EXACT INVERSE
======================================================================

Для каждого transformation режима Task46 определить математически точный
inverse.

Обязательный invariant:

    inverse(T(C, theta), theta) == C

byte-for-byte на canonical token sequence, с учётом documented boundary
semantics.

Добавить property tests.

======================================================================
7. BOUNDARY SEMANTICS
======================================================================

Явно определить:

    transformation whole corpus?
    per line?
    fixed blocks?
    incomplete final block?

Inverse обязан точно соответствовать forward Task46 implementation.

Не создавать "похожий" алгоритм отдельно.

По возможности вынести forward/inverse permutation mapping в shared
package.

======================================================================
8. SEARCH MODE
======================================================================

Создать standalone CLI, например:

    inverse-transposition-search

Input:

    canonical corpus
    search-space definition
    objective definition
    seed, если нужен
    output directory

Output:

    ranked candidate transformations
    transformed candidate corpora
    metrics
    search manifest
    report.

Не включать search в основной scientific pipeline.

======================================================================
9. OBJECTIVE
======================================================================

Objective должен быть multi-metric.

Не использовать единственный Task52 total distance.

Предварительно рассмотреть:

    transition structure
    relation significance
    sequence significance
    replicated profiles
    higher-order structure

только если forward audit подтверждает их transposition sensitivity.

Lexical metrics:

    N
    V
    frequency spectrum
    hapax

для pure token transposition должны оставаться invariants и НЕ должны
служить optimization target.

======================================================================
10. NO VOYNICH-TUNED WEIGHTS
======================================================================

Weights objective фиксируются до Voynich search.

Допустимые варианты:

    equal weights
    family-balanced weights

после control calibration.

Запрещено менять weights после просмотра Voynich candidates с целью
получить более красивый optimum.

======================================================================
11. CONTROL RECOVERY TEST
======================================================================

Для:

    C' = T8(Doyle)

search должен определить правильный или structural-equivalent inverse
candidate.

Проверить два результата отдельно.

A. Cryptographic recovery:

    найден ли настоящий theta?

B. Structural recovery:

    candidate metrics вернулись к natural-text regime?

Если правильный theta невозможно определить из-за эквивалентных
permutations, документировать equivalence classes.

======================================================================
12. BLIND VALIDATION
======================================================================

Желательно создать несколько synthetic transformed corpora с параметрами,
не переданными search evaluator.

Например агент/fixture генерирует:

    T3
    T7
    T11

Search знает allowed parameter range, но не true theta.

Измерить:

    top-1 recovery
    top-k recovery
    structural recovery.

======================================================================
13. NEGATIVE CONTROLS
======================================================================

Search также должен работать на:

    untransformed Doyle
    Longfellow или другом natural corpus.

Он не должен обязательно "находить улучшение".

Если optimizer всегда способен значительно улучшить objective даже на
обычном тексте, objective непригоден.

======================================================================
14. NULL SEARCH
======================================================================

Добавить random-permutation controls с тем же количеством candidate
evaluations.

Цель:

оценить, насколько improvement выбранной transposition family превосходит
случайный search.

Не интерпретировать лучший candidate без null distribution.

======================================================================
15. TRAIN / HOLDOUT ДЛЯ VOYNICH
======================================================================

Voynich нельзя оптимизировать целиком и затем на нём же оценивать
результат.

Определить deterministic split:

    discovery partition
    holdout partition

с сохранением meaningful boundaries насколько позволяет corpus.

На discovery:

    выбрать theta*

На holdout:

    применить тот же theta*
    БЕЗ переоптимизации.

Главный результат:

    воспроизводится ли structural improvement на holdout?

======================================================================
16. НЕ ПОДБИРАТЬ WIDTH ОТДЕЛЬНО ДЛЯ HOLDOUT
======================================================================

Если discovery дал:

    width = W*

holdout получает:

    W*

без нового search.

Иначе это не validation.

======================================================================
17. MULTIPLE CORPUS REGIONS
======================================================================

Если возможно без нарушения текущей corpus semantics, провести
дополнительную stability проверку:

    first/second half
    odd/even logical blocks
    several contiguous regions.

Нас интересует transformation, которая работает глобально, а не
случайный локальный optimum.

======================================================================
18. OUTPUT CANDIDATES
======================================================================

Для top candidates сохранять reconstructed corpus.

Например:

    candidate_w004.txt
    candidate_w007.txt

с transformation manifest.

Но НЕ запускать автоматически весь 28-stage pipeline для каждого
candidate.

Search должен использовать только необходимый diagnostic subset.

======================================================================
19. TWO-PHASE COMPUTATION
======================================================================

Phase A:

    cheap screening metrics

для всех candidates.

Phase B:

    expensive scientific validation

только для заранее определённого top-K.

Top-K фиксировать до Voynich run.

Это важно для computational feasibility.

======================================================================
20. EXISTING DISTRIBUTED EXECUTOR
======================================================================

Если candidate evaluations независимы, использовать существующую
remote-execution infrastructure.

Natural work unit:

    transformation candidate theta

или:

    candidate × validation partition.

Результат должен быть deterministic независимо от worker count/order.

Не создавать новый network protocol без необходимости.

======================================================================
21. REPRODUCIBILITY
======================================================================

Search manifest должен фиксировать:

    source corpus SHA256
    code git commit
    search-space version
    exact candidate parameter space
    objective version
    metric definitions
    weights
    discovery/holdout split
    seeds
    worker configuration
    top-K policy.

======================================================================
22. TASK52 INTEGRATION
======================================================================

После выбора небольшого числа candidates разрешается анализировать их
полным pipeline и передавать frozen experiment directories в Task52.

Но Task52 НЕ используется как black-box optimizer.

Он используется только для final comparison.

======================================================================
23. SUCCESS CRITERIA
======================================================================

Положительный результат Voynich search требует НЕ просто лучшего candidate.

Нужно одновременно:

1. meaningful improvement на discovery;
2. improvement нескольких independent transposition-sensitive metrics;
3. same-direction improvement на holdout;
4. superiority относительно random/null search;
5. transformation из заранее определённого simple family;
6. отсутствие изменения lexical invariants pure transposition;
7. отсутствие аналогичного систематического "улучшения" обычных
   untransformed controls.

======================================================================
24. NEGATIVE RESULT
======================================================================

Отрицательный результат также является scientific result.

Например:

    "rectangular columnar transpositions width 2–16 не восстанавливают
     устойчивую natural-text-like sequential structure Voynich."

Сохранить такой результат с тем же provenance, что положительный.

======================================================================
25. НЕ ДЕЛАТЬ
======================================================================

НЕ:

- искать произвольную permutation из N tokens;
- использовать genetic algorithm на unrestricted permutation space;
- оптимизировать непосредственно расстояние до Doyle;
- подбирать objective после Voynich results;
- использовать lexical vocabulary growth как target pure transposition;
- менять token identities;
- менять scientific thresholds;
- менять pipeline parameters для отдельных candidates;
- считать визуально "осмысленные" фрагменты доказательством;
- объявлять найденный candidate дешифровкой.

======================================================================
26. VALIDATION
======================================================================

Выполнить:

    go build ./...
    go vet ./...
    go test ./...
    go test -race ./...
    git diff --check

Property tests:

    inverse(forward(C, theta), theta) == C

для всех поддержанных modes/widths.

Control tests:

    synthetic known-transposition recovery.

======================================================================
DELIVERABLES
======================================================================

1. Shared exact forward/inverse transposition implementation.
2. inverse-transposition-search CLI.
3. INVERSE_TRANSPOSITION_METRIC_AUDIT.md.
4. Pre-registered objective definition.
5. Synthetic recovery benchmark.
6. Negative/null controls.
7. Discovery/holdout framework.
8. Distributed candidate evaluation where justified.
9. Search manifest/provenance.
10. Ranked candidate report.
11. Prepared top candidate corpora for optional full pipeline analysis.

======================================================================
DEFINITION OF DONE
======================================================================

Task54 завершён, когда инструмент:

- точно обращает известные Task46 transpositions;
- способен blind-recover synthetic transposition controls;
- не использует original plaintext как optimization target;
- имеет objective, зафиксированный до Voynich search;
- умеет оценивать null/random-search baseline;
- разделяет Voynich discovery и holdout;
- выдаёт deterministic ranked candidates;
- позволяет строго проверить ограниченную гипотезу о transposition,
  не превращаясь в unrestricted optimizer.
