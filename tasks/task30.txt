Task30 — Distributed Execution Feasibility Audit

Цель: определить, как распараллелить production-run после оптимизаций Task29, не меняя вычислительную модель, RNG semantics и результаты.

Важно: на этом этапе не реализовывать distributed execution. Задача — провести аудит текущего pipeline и подготовить конкретный план реализации на основании нового профиля после Task29.

1. Новый performance profile

Запустить production-equivalent benchmark/profile на текущей версии после Task29.

Зафиксировать:

wall time;
CPU time;
peak HeapAlloc / RSS;
top CPU hotspots;
allocation hotspots;
долю времени по основным стадиям pipeline;
отдельно время, приходящееся на permutation/resampling workload.

Сохранить профили в profiles/.

2. Найти естественные единицы параллелизма

Исследовать возможность независимого выполнения на уровнях:

corpus;
method;
scale;
K;
permutation/replicate;
комбинаций этих измерений.

Для каждого варианта определить:

какие данные являются read-only shared input;
какое состояние локально для worker;
существуют ли зависимости между jobs;
объём входных/выходных данных;
стоимость сериализации;
насколько равномерны jobs по CPU time;
подходит ли уровень для локального multiprocessing и для распределения между машинами.

Предпочтение должно отдаваться крупнейшей независимой единице, обеспечивающей достаточный parallelism без чрезмерного IPC/network overhead.

3. RNG audit

Это критическая часть задачи.

Проследить полный lifecycle RNG:

где создаются seeds;
где и в каком порядке потребляются random numbers;
зависит ли RNG stream от порядка выполнения replicates;
существуют ли shared/global RNG states;
можно ли вычислять replicate независимо;
можно ли детерминированно получить seed/state для конкретного job.

Не менять RNG algorithm или seed derivation в рамках Task30.

Определить, возможно ли распределённое выполнение с сохранением текущего результата.

4. Reduction / aggregation audit

Проверить, как результаты отдельных jobs объединяются.

Определить:

зависит ли результат от порядка aggregation;
используются ли floating-point reductions;
может ли изменение порядка сложения изменить output;
требуется ли canonical ordering;
можно ли reducer сделать order-independent;
какие промежуточные результаты необходимо возвращать worker'у.

Особое внимание уделить ситуациям, где математически эквивалентная параллельная реализация перестаёт быть побитово идентичной из-за floating-point arithmetic.

5. Bit-for-bit reproducibility

Главный критерий будущей реализации:

Distributed execution must produce outputs bit-for-bit identical to the current optimized single-process implementation for the same input, parameters and seed.

Определить, возможно ли выполнить это требование.

Если невозможно — точно указать:

где возникает расхождение;
почему;
насколько оно фундаментально;
можно ли изменить архитектуру распределения так, чтобы сохранить идентичность.

Не ослаблять критерий самостоятельно до numerical/statistical equivalence.

6. Worker resource model

Оценить ресурсы одного worker:

CPU;
peak RAM;
read-only shared data;
mutable/private data;
temporary allocations;
размер job input;
размер job result.

Отдельно оценить:

несколько workers в одном процессе;
несколько процессов на одной машине;
workers на разных машинах.

Проверить, можно ли эффективно разделять dense structures, созданные в Task29, между локальными workers без их полного копирования.

7. Scaling model

На основании измерений построить прогноз для:

1 worker;
2;
4;
8;
16;

Использовать измеренную parallel fraction и Amdahl's law, а не предполагать линейное масштабирование.

Для каждого варианта дать:

theoretical wall time;
realistic wall-time estimate;
CPU-hours;
estimated RAM;
ожидаемую parallel efficiency.

Отдельно указать вероятную точку diminishing returns.

8. Архитектурные варианты

Сравнить минимум три варианта:

A. Local goroutine worker pool

Один процесс, shared memory.

B. Local multi-process execution

Несколько независимых процессов на одной машине.

C. Distributed workers

Несколько машин с coordinator/job queue/reducer.

Для каждого оценить:

сложность реализации;
reproducibility;
memory efficiency;
fault isolation;
scheduling;
retry semantics;
network/storage requirements;
пригодность для запуска большого числа corpora.

Не добавлять внешнюю инфраструктуру вроде Kubernetes, Redis, Kafka и т. п. без доказанной необходимости.

9. Fault/retry semantics

Определить требования к будущей системе:

идентификатор job;
deterministic retry;
duplicate execution;
partial failure;
worker crash;
coordinator crash;
checkpoint/resume;
atomic publication результатов.

Повторный запуск одного job должен давать тот же результат.

10. Итоговая рекомендация

Подготовить конкретную архитектуру Task31.

Ответить:

Что именно должно быть unit of work?
Где должен находиться RNG state?
Что получает worker?
Что возвращает worker?
Как выполняется deterministic reduction?
Какой вариант выбрать для локального parallel execution?
Как расширить его до нескольких машин?
Какое ожидается ускорение production-run?
Сколько workers имеет практический смысл?
Можно ли гарантировать bit-for-bit compatibility?
Ограничения

В Task30:

не менять scientific/statistical algorithms;
не менять RNG algorithm/semantics;
не менять output formats;
не оптимизировать код попутно;
не реализовывать worker pool;
не добавлять distributed dependencies;
не принимать numerical equivalence вместо bit-for-bit equivalence;
все выводы о производительности подтверждать измерениями.
Проверки

После аудита существующий код должен по-прежнему проходить:

go vet ./...
go test ./...
go test -race ./internal/conditionalregime
git diff --check
