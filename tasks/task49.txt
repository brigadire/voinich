Task49 — Vocabulary Growth / Heaps-Law Analysis

Цель

Добавить в scientific analysis system новый corpus-level анализатор,
исследующий рост vocabulary по мере чтения корпуса.

Основной научный вопрос:

    Почему Voynich при сравнительно небольшом corpus size имеет
    аномально большое число unique token types?

Нужно определить, отличается ли Voynich от control corpora:

- абсолютным vocabulary size;
- скоростью появления новых token types;
- формой vocabulary-growth trajectory;
- количеством и динамикой hapax/dis legomena;
- локальной продуктивностью новых форм;
- параметрами Heaps law;
- устойчивостью этих свойств относительно позиции в corpus.

Анализ должен быть language-agnostic.

======================================================================
1. НОВЫЙ CLI
======================================================================

Создать отдельный scientific CLI, например:

    vocabulary-growth-analyze

Input:

    canonical corpus

Output directory:

    стандартный experiment stage directory / output convention проекта.

CLI должен использовать существующие corpus-loading и profiling packages,
а не создавать альтернативную tokenization implementation.

======================================================================
2. ОСНОВНАЯ TRAJECTORY
======================================================================

Для последовательности tokens:

    t1, t2, ..., tN

вычислить:

    V(n) = число distinct token types среди t1...tn

Не обязательно сохранять значение для каждого n.

Поддержать deterministic checkpoints.

Предпочтительно использовать логарифмически плотную сетку плюс
scientifically useful fixed checkpoints.

Например:

    100
    200
    500
    1 000
    2 000
    4 000
    8 000
    16 000
    32 000
    ...

и обязательно:

    N = full corpus size.

Но НЕ hardcode 39026.

Grid должна автоматически адаптироваться к corpus size.

Для короткого corpus использовать все доступные checkpoints <= N.

======================================================================
3. HEAPS LAW
======================================================================

Оценить модель:

    V(n) = K * n^beta

или:

    log V(n) = log K + beta log n

Сохранить:

    K
    beta
    fit R²
    residual diagnostics
    fitting range

Не считать хороший fit доказательством естественного языка.

Heaps fit — descriptive metric.

======================================================================
4. LOCAL / EFFECTIVE BETA
======================================================================

Глобальная beta может скрывать изменение режима.

Вычислить локальную скорость роста:

    beta_eff(n) =
        Δ log V / Δ log n

между соседними достаточно удалёнными checkpoints.

Сохранить trajectory:

    n
    V(n)
    beta_eff

Это позволит увидеть:

- насыщается ли vocabulary;
- остаётся ли production rate высокой;
- существуют ли regime changes.

======================================================================
5. NEW-TYPE RATE
======================================================================

Для последовательных окон вычислять:

    new_types(window)

и:

    new_type_rate =
        new token types / tokens in window

Пример:

    tokens 0–1999
    tokens 2000–3999
    ...

Window sizes не должны быть завязаны на Voynich.

Поддержать несколько relative/fixed scales, согласованных с
существующей системой scientific parameters.

Минимально:

    500
    1000
    2000

если corpus size позволяет.

======================================================================
6. FREQUENCY-OF-FREQUENCIES
======================================================================

На каждом крупном checkpoint считать:

    V1 = types occurring exactly once
    V2 = types occurring exactly twice
    V3
    V4
    V5+

Особенно сохранить:

    hapax_count
    hapax_fraction_of_types
    hapax_fraction_of_tokens

и аналогично dis legomena.

Это позволит отличить:

    большой стабильный vocabulary

от:

    постоянного производства одноразовых форм.

======================================================================
7. FINAL VOCABULARY PROFILE
======================================================================

Для полного corpus сохранить:

    total_tokens
    unique_tokens
    type_token_ratio

    hapax
    dis_legomena
    tris_legomena

    hapax / vocabulary
    hapax / tokens

    singleton-to-doubleton ratio

    Heaps K
    Heaps beta
    Heaps R²

Не использовать TTR как основную cross-corpus metric без поправки
на corpus size.

======================================================================
8. ORDER DEPENDENCE
======================================================================

Классическая Heaps trajectory зависит от порядка текста.

Это для нас одновременно сигнал и потенциальный confounder.

Поэтому вычислить:

A. observed trajectory — исходный порядок corpus;

B. shuffled-token null trajectories.

Для shuffled null:

    сохраняется полный token multiset;
    уничтожается document order.

Выполнить permutation ensemble с deterministic seeds.

Для каждого checkpoint получить:

    observed V(n)
    null mean
    null SD
    percentile / empirical p
    standardized effect

Это покажет, является ли необычная vocabulary-growth trajectory
следствием распределения типов по документу, а не только общей
frequency distribution.

======================================================================
9. BLOCK-SHUFFLE NULL
======================================================================

Если вычислительно оправдано, добавить второй null:

    block shuffle

который сохраняет локальную структуру внутри blocks,
но меняет крупномасштабный порядок.

Block sizes должны быть параметрами.

Это позволит различать:

    local lexical clustering

и:

    document-scale vocabulary organization.

Если реализация существенно расширяет Task49 — сначала сделать audit
и оставить block-null как Phase 2.

======================================================================
10. SUBSAMPLE / LENGTH-NORMALIZED COMPARISON
======================================================================

Очень важное требование.

Corpus sizes различаются.

Анализ должен поддерживать сравнение при общей длине:

    N_common = min(corpus sizes)

Но сам vocabulary-growth-analyze работает с ОДНИМ corpus.

Он должен поэтому сохранять trajectory достаточно полно, чтобы
Task45 / experiment-compare мог позднее сравнить:

    V_A(n) vs V_B(n)

на одинаковых n.

НЕ обрезать длинный corpus физически.

НЕ создавать truncated corpus.

Comparison layer должен брать значения trajectory до общего N.

======================================================================
11. POSITIONAL ROBUSTNESS
======================================================================

Чтобы результат не зависел исключительно от начала документа,
добавить segment analysis.

Разделить corpus на, например:

    4
    8

равных contiguous segments, если размер позволяет.

Для каждого segment вычислить локальную vocabulary growth trajectory
от начала данного segment.

Сравнить beta / new-type rate между segments.

Это позволит увидеть:

    "богатый словарь только в herbal section"

или:

    "высокая продуктивность присутствует по всему Voynich".

Не использовать metadata Voynich sections внутри generic algorithm.

Segmentation исключительно positional.

======================================================================
12. CORPUS-SIZE SAFETY
======================================================================

Никаких предположений:

    N == 39026
    N >= 39026

или других Voynich-specific constants.

Тестировать минимум:

    N = 1
    N = 100
    N = 1000
    N = 8000
    N = 39026
    N = 85000
    N = 120000

Короткий corpus должен либо корректно анализироваться,
либо конкретная unavailable metric должна получать NOT_APPLICABLE.

Не падать из-за отсутствия больших checkpoints.

======================================================================
13. DISTRIBUTED EXECUTION AUDIT
======================================================================

Сначала реализовать/profile single-machine core.

Базовая observed Heaps trajectory вычисляется за O(N) и, вероятно,
НЕ требует distribution.

Не распределять дешёвые операции только потому, что remote executor есть.

После profiling определить стоимость:

    observed trajectory
    shuffle null
    block null
    segment analysis
    bootstrap/permutation inference

Natural distributed unit для null ensemble, скорее всего:

    permutation replicate

Если permutations становятся dominant cost, использовать существующий
distributed executor.

24. TRANSFORMED CORPORA
======================================================================

После завершения Task46 этот stage должен без изменений работать на:

    transposition corpora
    homophonic corpora

Это особенно важно.

Ожидания НЕ кодировать в программу, но экспериментально мы сможем
проверить:

Token-level transposition:

    final vocabulary invariant

но vocabulary-growth trajectory может измениться из-за перестановки.

Homophonic:

    final vocabulary увеличивается

и trajectory должна существенно измениться.

Это даст дополнительный mechanistic discriminator.

26. PERFORMANCE
======================================================================

Observed trajectory должна быть O(N) expected time и O(V) memory.

Не реализовывать очевидно O(N*V) algorithm.

Frequency-of-frequencies обновлять incrementally:

при переходе frequency:

    f -> f+1

обновлять соответствующие counters без полного пересчёта vocabulary.

Permutation computation также проектировать с учётом повторного
использования buffers и минимизации allocations.

Сначала profile, затем оптимизировать.

======================================================================
DEFINITION OF DONE
======================================================================

Task49 завершён, когда система может для любого canonical corpus
детерминированно измерить не только итоговый vocabulary size, но и
траекторию его роста V(N), параметры Heaps law, динамику hapax/new types
и отличие observed trajectory от order-destroying null models.

Stage работает без знания языка и без Voynich-specific constants,
интегрирован в новую версию pipeline, не ломает frozen experiments и
может использовать существующий distributed executor для действительно
тяжёлых permutation computations.
