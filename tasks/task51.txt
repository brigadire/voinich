Task51 — Right-to-Left / Orientation Corpus Transformation

Цель

Создать отдельную deterministic utility для построения вариантов корпуса
с обратной ориентацией последовательности.

Основная исследовательская гипотеза:

    Наблюдаемое направление текста Voynich слева направо может не
    соответствовать логическому направлению исходной последовательности.

Необходимо создать преобразованные корпуса, позволяющие проверить влияние:

1. порядка токенов внутри строки;
2. порядка glyph/символов внутри токена;
3. одновременного обращения обоих уровней.

Полученные корпуса впоследствии анализируются существующим scientific
pipeline как независимые experiments.

Утилита НЕ должна выполнять scientific analysis сама.

======================================================================
1. НОВАЯ УТИЛИТА
======================================================================

Создать standalone CLI, например:

    codex_orientation

или, если в проекте уже существует общий transformation framework после
Task46:

    codex_transform orientation

Предпочесть существующий transformation framework, если это не создаёт
архитектурного дублирования.

Input:

    canonical corpus

Output:

    transformed canonical corpus
    transformation manifest

======================================================================
2. ОСНОВНЫЕ РЕЖИМЫ
======================================================================

Поддержать минимум три преобразования.

A. TOKEN_REVERSE

Исходная строка:

    daiin ol chedy qokeedy

Результат:

    qokeedy chedy ol daiin

Меняется только порядок whitespace-delimited tokens внутри каждой строки.

Содержимое каждого token остаётся byte/Unicode-identical.

------------------------------------------------------------

B. GLYPH_REVERSE

Исходная строка:

    daiin ol chedy qokeedy

Результат:

    niiad lo ydehc ydeekoq

Порядок tokens сохраняется.

Порядок Unicode code points внутри каждого token обращается.

------------------------------------------------------------

C. FULL_REVERSE

Исходная строка:

    daiin ol chedy qokeedy

Результат:

    ydeekoq ydehc lo niiad

То есть:

    reverse token order
    +
    reverse glyph order inside tokens

Это эквивалентно логическому зеркальному обращению содержимого строки
при сохранении самой строки как structural unit.

======================================================================
3. НЕ МЕНЯТЬ ПОРЯДОК СТРОК
======================================================================

В Task51 НЕ обращать:

    line order
    page order
    folio order

Строка является единицей orientation transformation.

То есть:

    line1: A B C
    line2: D E F

TOKEN_REVERSE:

    line1: C B A
    line2: F E D

но НЕ:

    line2
    line1

Если позднее понадобится reverse-line-order/page-order, это отдельный
эксперимент и отдельная transformation mode/version.

======================================================================
4. SCIENTIFIC RATIONALE
======================================================================

TOKEN_REVERSE является главным экспериментальным режимом.

Он должен сохранять точно:

    total token count
    vocabulary
    token frequencies
    hapax/dis-legomena counts
    token lengths
    character composition

и изменять только directional sequence structure внутри строк.

Следовательно, это controlled intervention для проверки:

    transition directionality
    begin/end relations
    directional context
    higher-order sequences
    positional continuation
    transition network
    local sequential structure

GLYPH_REVERSE дополнительно проверяет зависимость результатов от
внутритокенной orientation.

FULL_REVERSE проверяет совместное изменение обоих уровней.

======================================================================
5. CANONICAL CORPUS COMPATIBILITY
======================================================================

Input должен соответствовать canonical generic corpus format,
определённому codex_prepare.

Использовать существующий shared validator.

Не создавать альтернативную tokenization implementation.

При invalid corpus:

    fail closed

Не исправлять input автоматически.

======================================================================
6. UNICODE
======================================================================

GLYPH_REVERSE должен быть Unicode-safe.

Минимально:

    reverse by Unicode code points / runes

а не bytes.

До реализации проверить, встречаются ли combining characters в
поддерживаемых canonical corpora.

Если combining sequences возможны и reversal по rune способен разрушить
grapheme cluster, документировать это и, если практически оправдано,
использовать grapheme-cluster reversal.

Для EVA/ASCII Voynich это не должно изменять scientific semantics.

Никогда не обращать UTF-8 bytes напрямую.

======================================================================
7. LINE BOUNDARIES
======================================================================

Сохранять:

    количество logical lines
    порядок lines

Не переносить token между строками.

Пустые строки, если canonical format их допускает, сохранять
детерминированно согласно существующей corpus policy.

Это принципиально:

    TOKEN_REVERSE должен моделировать right-to-left interpretation
    каждой строки,

а не глобальный reverse всего файла.

======================================================================
8. OUTPUT NAMING
======================================================================

Пример:

Input:

    data_work/ZL3b-x7.txt

Outputs:

    ZL3b-x7.token-reverse.txt
    ZL3b-x7.glyph-reverse.txt
    ZL3b-x7.full-reverse.txt

Но CLI должен позволять явно задавать output path.

Если output существует:

======================================================================
9. TRANSFORMATION MANIFEST
======================================================================

Для каждого output создать manifest, например:

    <output>.transform.json

Минимальные поля:

    schema_version
    transformation: orientation
    transformation_version

    mode:
        TOKEN_REVERSE
        GLYPH_REVERSE
        FULL_REVERSE

    input_path
    input_sha256
    output_path
    output_sha256

    input_tokens
    output_tokens

    input_unique_tokens
    output_unique_tokens

    input_lines
    output_lines

    token_order_reversed: true/false
    glyph_order_reversed: true/false
    line_order_reversed: false

    deterministic: true

Если существует общий manifest schema Task46, использовать его.

======================================================================
10. INVARIANTS
======================================================================

TOKEN_REVERSE обязан сохранять:

    N
    V
    frequency каждого token
    multiset tokens
    line count
    token count per line

Проверять эти invariants программно после transformation.

GLYPH_REVERSE обязан сохранять:

    N
    line count
    token count per line
    token-length multiset

При этом vocabulary/token frequencies могут измениться из-за возможных
совпадений reversed forms, поэтому НЕ требовать сохранения V.

FULL_REVERSE имеет те же invariants, что GLYPH_REVERSE относительно
token identity.

======================================================================
11. REVERSIBILITY
======================================================================

Это особенно полезный correctness oracle.

Для каждого режима:

    T(T(C)) == C

byte-for-byte для canonical input.

Проверить:

    TOKEN_REVERSE(TOKEN_REVERSE(C)) == C
    GLYPH_REVERSE(GLYPH_REVERSE(C)) == C
    FULL_REVERSE(FULL_REVERSE(C)) == C

Это обязательные tests.

======================================================================
12. ORIGINAL CORPUS НЕ МЕНЯТЬ
======================================================================

Утилита никогда не должна модифицировать source corpus.

Transformation:

    C -> C'

является созданием нового scientific input.

Original SHA256 должен оставаться неизменным.

======================================================================
13. PIPELINE INTEGRATION
======================================================================

НЕ добавлять orientation transformation как scientific stage.

Workflow должен быть:

    canonical Voynich corpus
            |
            +--> TOKEN_REVERSE corpus
            |
            +--> GLYPH_REVERSE corpus
            |
            +--> FULL_REVERSE corpus

после чего:

    pipeline-orchestrate manifest -generic-corpus ...
    pipeline-orchestrate run ...

для каждого transformed corpus.

Каждый вариант является отдельным experiment.

======================================================================
14. EXPERIMENT PROVENANCE
======================================================================

Если pipeline-orchestrate уже поддерживает provenance от Task46/codex_prepare,
расширить его так, чтобы manifest нового experiment мог зафиксировать:

    source corpus SHA256
    transformed corpus SHA256
    transformation manifest SHA256
    transformation type
    transformation mode

Scientific identity определяется фактическим transformed corpus SHA256.

Не делать provenance обязательным для обычных generic corpora.

======================================================================
15. VOYNICH METADATA
======================================================================

Основной эксперимент должен выполняться над тем же canonical token corpus,
который использовался для frozen Voynich baseline.

Не использовать IVTFF metadata для самого преобразования.

В частности, transformer не должен знать:

    Currier language
    hand
    folio
    section
    illustration type

Единственная structural information:

    logical line boundaries уже существующего corpus.

======================================================================
20. DIRECTIONAL METRIC AUDIT
======================================================================

До интерпретации результатов составить краткий список существующих
scientific metrics:

    invariant under TOKEN_REVERSE
    theoretically transformed/predictably swapped
    genuinely orientation-sensitive
    uncertain

Создать:

    ORIENTATION_METRIC_AUDIT.md

Это необходимо сделать ДО просмотра comparative results, чтобы избежать
post-hoc interpretation.

Например, проверить, какие left/right metrics должны просто поменяться
местами при exact reversal.

Если математически ожидается:

    left_profile(original) == right_profile(reversed)

это использовать как дополнительный correctness oracle.

======================================================================
21. CROSS-LINE RELATIONS
======================================================================

Провести audit существующего pipeline:

какие stages считают переход:

    last token line N -> first token line N+1

При TOKEN_REVERSE такой cross-line transition не является простым
обращением исходного перехода.

Документировать это отдельно.

Не менять существующую scientific semantics pipeline в Task51.

Это важное ограничение интерпретации результатов.

DEFINITION OF DONE
======================================================================

Task51 завершён, когда из frozen canonical Voynich corpus можно
детерминированно получить три independent scientific inputs:

    token-reverse
    glyph-reverse
    full-reverse

с полностью зафиксированным provenance.

TOKEN_REVERSE сохраняет exact token multiset и меняет только порядок
tokens внутри logical lines.

Все transformations являются involutions:

    T(T(C)) == C

Existing scientific pipeline и distributed executor могут анализировать
полученные corpora без специальных изменений, а frozen Voynich baseline
остаётся неизменным.
