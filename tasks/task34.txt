Task34 — mTLS PKI and Worker Authentication

Goal

Add mutual-TLS authentication to the already implemented Task33 remote distributed executor. The coordinator authenticates every worker using an individual client certificate signed by a project-controlled CA; every worker authenticates the coordinator through the same project PKI.

This task includes generation of the project CA and issuance of coordinator and worker certificates. It is transport/security work only: do not alter JobID, RNG, scientific computation, scheduling semantics, deterministic reduction, checkpoints, or scientific outputs.

Primary invariants

1. Workers without a valid project-issued client certificate are rejected.
2. Workers reject coordinators with an invalid chain or wrong server identity.
3. Every worker has its own certificate/key.
4. Worker identity comes from the verified certificate, not an untrusted request field.
5. Certificate renewal/replacement cannot affect scientific output.
6. ca.key is not required on coordinator or workers during normal operation.

PKI

Project CA:
  ca.crt
  ca.key

Issued credentials:
  coordinator.crt / coordinator.key   (serverAuth)
  worker-N.crt / worker-N.key         (clientAuth)

The CA private key must remain offline/separate from runtime nodes.

Phase 1 — Audit Task33 transport

Document coordinator API/listener, worker connection flow, existing TLS/identity mechanisms, endpoints requiring authentication and any bearer/API-key assumptions.

Phase 2 — CA generation

Add an administrative command/tool generating ca.crt and ca.key.

Requirements:
- modern Go-supported key/signature algorithm;
- correct CA Basic Constraints and Key Usage;
- configurable validity with sane default;
- restrictive key permissions;
- refuse overwrite unless explicitly forced;
- never automatically copy ca.key to runtime nodes.

Document ca.key backup/security.

Phase 3 — Coordinator certificate issuance

Issue coordinator.crt/coordinator.key signed by the project CA.

Requirements:
- EKU serverAuth;
- mandatory explicit DNS/IP SANs;
- no reliance on Common Name;
- configurable validity;
- unique serial;
- restrictive key permissions.

Phase 4 — Worker certificate issuance

Issue unique worker-N.crt/worker-N.key.

Requirements:
- EKU clientAuth;
- unique worker identity in a documented certificate field, preferably URI SAN;
- validate identity format;
- unique serial;
- restrictive key permissions;
- no shared worker certificate.

Phase 5 — Coordinator mTLS enforcement

Coordinator must:
- present coordinator certificate/key;
- trust only configured project CA(s);
- require and verify client certificates;
- reject missing, expired, invalid, wrong-EKU or untrusted certificates;
- derive WorkerID from the verified peer certificate.

If protocol still carries worker_id, it must not be authoritative and must match authenticated identity if retained.

Phase 6 — Worker verification

Worker configuration must include ca.crt, worker certificate/key and coordinator HTTPS URL.

Worker must:
- verify coordinator chain and SAN/server name;
- present its client certificate;
- fail closed;
- have no production insecure-skip-verify path.

Phase 7 — Lifecycle/revocation

Document/support:
- adding worker;
- renewing worker;
- renewing coordinator;
- compromised worker replacement;
- CA rotation.

Implement the minimum justified revocation mechanism. At minimum support an explicit coordinator deny/revocation list by certificate serial and/or authenticated worker identity if CRL/OCSP is disproportionate.

Phase 8 — Identity separation

Preserve:
  JobID    = scientific computation identity
  WorkerID = authenticated executor identity
  LeaseID  = execution attempt identity

Worker certificate identity must never participate in JobID, replicateSeed, RNG, statistics or reduction.

Phase 9 — Security tests

Cover:
- valid worker accepted;
- missing client cert rejected;
- foreign CA rejected;
- expired/not-yet-valid cert rejected where practical;
- wrong EKU rejected;
- wrong coordinator SAN rejected;
- malformed worker identity rejected;
- identity derived from certificate;
- request cannot impersonate another WorkerID;
- revoked worker rejected if implemented;
- renewal does not affect scientific result.

Phase 10 — Reproducibility

Run the Task33 oracle with:
1. existing reference;
2. mTLS worker certificate A;
3. renewed certificate;
4. same job retried on another authenticated worker.

All scientific artifacts must remain SHA256-identical.

Phase 11 — CLI/config

Provide explicit settings following existing conventions, conceptually:

Coordinator:
  -tls-cert coordinator.crt
  -tls-key coordinator.key
  -client-ca ca.crt

Worker:
  -ca ca.crt
  -tls-cert worker.crt
  -tls-key worker.key
  -coordinator https://...

Never log private keys/secrets.

Phase 12 — Documentation

Update DISTRIBUTED_EXECUTION_OPERATIONS.md and DISTRIBUTED_EXECUTION_IMPLEMENTATION.md with complete CA creation, server/worker issuance, placement, startup, renewal, compromise and CA-key-storage procedures.

Constraints

- No scientific/statistical/RNG/JobID/reduction changes.
- No bearer token as substitute for client-certificate authentication.
- No shared worker certificate.
- No ca.key on runtime workers or required by coordinator runtime.
- No insecure production TLS mode.
- No heavyweight external PKI requirement.

Validation

go build ./...
go vet ./...
go test ./...
go test -race ./internal/conditionalregime
git diff --check

Run all new TLS integration tests and existing Task33 distributed correctness tests.

Definition of Done

Task34 is complete when CA generation and coordinator/worker issuance are implemented and documented; coordinator requires verified individual worker certificates; workers verify coordinator identity; WorkerID comes from the certificate; ca.key stays outside runtime nodes; renewal/retry preserves byte-identical results; and all security/integration/race tests pass.
