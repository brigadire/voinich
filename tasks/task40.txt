Task40 — Distributed execution for structural-projection-analyze

Цель

Распределить наиболее дорогую corpus-generic стадию
`structural-projection-analyze` по существующей remote execution
инфраструктуре.

На production Voynich эта стадия занимает порядка 3 часов и будет
выполняться для каждого comparative corpus. Основной кандидат для
распределения — независимые random projection trials
(`-random-projections`, production value = 200).

Критическое требование:

LOCAL / PROCESS / REMOTE должны давать byte-for-byte identical scientific
outputs при одинаковых corpus, parameters и seed.

Не менять scientific algorithm ради ускорения.

--------------------------------------------------
1. Profile first
--------------------------------------------------

Перед изменениями снять свежий профиль текущего HEAD:

- Voynich corpus;
- data_test/pg2097-2.txt;
- production scientific parameters;
- допускается уменьшить random-projections только для profiling run.

Зафиксировать:

- serial preparation time;
- время random-projection loop;
- время final reduction/output;
- CPU hotspots;
- allocation hotspots;
- peak/live memory;
- фактическую долю времени, потенциально доступную для распределения.

Не использовать старые оценки вместо свежего измерения.

--------------------------------------------------
2. Audit parallelism
--------------------------------------------------

Проверить и документально подтвердить независимость projection trial.

Для каждого trial определить все входы:

    corpus
    frozen analysis state
    base seed
    trial index
    scientific parameters

RNG должен быть воспроизводимой функцией:

    trialSeed = f(baseSeed, trialIndex)

или существующим эквивалентом.

Результат trial N не должен зависеть от:

- порядка выполнения trials;
- worker identity;
- количества workers;
- завершения предыдущих trials;
- retry;
- scheduling order.

Если текущий RNG является последовательным и это условие не выполняется,
сначала остановиться и описать проблему. Не менять RNG semantics без
доказательства byte-equivalence.

--------------------------------------------------
3. Audit shared mutable state
--------------------------------------------------

Особое внимание существующим reusable/package-level scratch buffers в
`structuralprojection`.

Ранее они были отмечены как потенциально небезопасные для concurrent
goroutine execution.

Проверить:

- package-level buffers;
- caches;
- mutable workspaces;
- global RNG;
- reused slices/maps;
- normalization scratch;
- metrics scratch.

Remote execution не должна создавать data races или nondeterminism.

Предпочтительный первоначальный вариант:

    один structural-projection trial одновременно
    на один worker process

если безопасный intra-process concurrency требует существенного rewrite.

Не увеличивать concurrency ценой корректности.

--------------------------------------------------
4. Reuse existing distributed infrastructure
--------------------------------------------------

НЕ создавать второй distributed framework.

Расширить существующую инфраструктуру Task31–35:

    coordinator
    mTLS
    JobID
    lease
    heartbeat/timeout
    retry
    worker identity
    deterministic result collection
    Ansible deployment

новым job type, например:

    structural_projection_trial

Job должен содержать только необходимые immutable inputs/identifiers.

Большие invariant datasets не пересылать заново с каждым trial, если
существующая worker initialization/staging архитектура позволяет
безопасно загрузить их один раз.

--------------------------------------------------
5. Deterministic JobID
--------------------------------------------------

JobID должен однозначно определяться scientific identity работы.

Например:

    experiment fingerprint
    stage
    trial index
    relevant frozen parameters

Worker hostname/IP НЕ является частью scientific identity.

Повторная выдача того же job после timeout должна вычислять тот же результат.

Duplicate result должен безопасно дедуплицироваться по JobID.

--------------------------------------------------
6. Canonical reduction
--------------------------------------------------

Это обязательная часть задачи.

Remote results могут приходить в любом порядке, но coordinator должен
восстановить:

    trial 0
    trial 1
    ...
    trial N-1

и только после этого выполнять существующий reduction.

Нельзя суммировать/усреднять float results в network arrival order.

Существующий local execution является oracle.

Не заменять bit-for-bit identity на numerical tolerance.

--------------------------------------------------
7. Executors
--------------------------------------------------

Добавить/сохранить единый интерфейс:

    goroutine
    process
    remote

если это соответствует существующей архитектуре.

Scientific core должен быть общим.

Executor отвечает только за transport/scheduling.

CLI желательно привести к существующему стилю:

    structural-projection-analyze \
        ... \
        -executor remote \
        -workers N \
        -remote-listen ... \
        -tls-cert ... \
        -tls-key ... \
        -client-ca ... \
        -remote-timeout ... \
        -remote-retries ...

Не обязательно копировать названия flags буквально, если общий executor
уже предоставляет другой API.

--------------------------------------------------
8. Worker support
--------------------------------------------------

Существующий worker binary/deployment должен уметь принимать новый job type.

Не создавать отдельную Ansible роль, если текущий worker можно расширить.

Task35 deployment/cleanup semantics сохранить:

    deploy
    run from /tmp
    remove completely

После cleanup на worker не должны оставаться:

- binary;
- corpus;
- temporary results;
- certificates/private keys;
- processes.

--------------------------------------------------
9. Fault tolerance
--------------------------------------------------

Проверить:

- worker dies during trial;
- lease timeout;
- connection loss;
- duplicate completion;
- coordinator receives late result after reassignment;
- worker joins after computation started;
- worker disappears permanently.

Retry не должен менять scientific result.

Run с искусственно убитым worker должен дать тот же output, что uninterrupted
local oracle.

--------------------------------------------------
10. Checkpoint/resume
--------------------------------------------------

Если `structural-projection-analyze` уже имеет checkpoint semantics —
расширить их на distributed trials.

Если нет — добавить минимальный crash-safe checkpoint completed trial IDs
и результатов, если это не меняет scientific output.

После restart coordinator не должен заново вычислять уже надёжно
зафиксированные trials.

Resume output должен быть byte-for-byte identical uninterrupted output.

--------------------------------------------------
11. Progress visibility
--------------------------------------------------

Текущий production run может часами не писать ничего в лог.

Добавить progress для этой стадии, например:

    structural projections 73/200
    workers active: 10
    outstanding: 10
    retries: 0
    elapsed: 00:41:12
    ETA: 01:07:30

Не засорять scientific outputs.

`-quiet` должен отключать progress.

Также pipeline-orchestrate должен оставлять понятный stage-level признак,
что stage жива, даже при долгом remote execution.

--------------------------------------------------
12. Correctness tests
--------------------------------------------------

Обязательные oracle tests:

A. local vs process
B. local vs remote
C. remote with 1 worker vs multiple workers
D. different scheduling order
E. retry after worker failure
F. interrupted + resumed vs uninterrupted
G. repeated same-seed runs
H. `go test -race`

Все persisted scientific outputs должны быть byte-for-byte identical.

- output schemas;

--------------------------------------------------
Definition of Done
--------------------------------------------------

`structural-projection-analyze` использует существующую mTLS distributed
execution infrastructure для независимых projection trials.

Результат:

    local == process == remote
    1 worker == N workers
    uninterrupted == resumed
    no-failure == retry-after-failure

побитово для всех scientific outputs.

Pipeline-orchestrate автоматически использует этот executor для stage 17
в generic и Voynich runs при соответствующей remote configuration.

Получены реальные scaling measurements на `data_test/pg2097-2.txt`.

Voynich frozen baseline остаётся неизменным.
