## Real defects this validation process caught (not fabricated, not hidden)

1. **`oracle_bb.py` incumbent-seeding bug**: the exact branch-and-bound oracle initialized its
   incumbent from the empty table's score, which let it silently answer a different question
   (best table of size <= `table_size`) than every other solver (best table of EXACTLY
   `table_size`). Caught by 10/100 disagreements against CP-SAT before the fix; 0/150 after.
2. **Non-deterministic seeding via Python's `hash()`**: `discriminative_benchmark.py` derived
   solver/baseline seeds from `hash(case_id)`, which is salted per-process
   (`PYTHONHASHSEED`) and not stable across runs. Caught by `safety_tests.py`'s
   `REPRODUCIBLE::discriminative_benchmark.py` check finding 8/10 cases' `RANDOM_BASELINE`
   fitness differed between two consecutive runs. Fixed with a SHA-256-based `stable_seed()`.
3. Two new historical-lexicon defects beyond what the frozen v3 audit had found (Alcor/Alnair
   anachronisms in the Vienna source, on top of the two it already knew about) and two more
   instances of the same misattribution pattern elsewhere in the lexicon (Markab/Scheat,
   Porrima/Zavijava) — see `LEXICON_REMEDIATION_REPORT.md` for details.
4. **`hybrid.py`'s `NEIGHBORHOOD` verifier: combinatorial-explosion hang (CRITICAL, caught live).**
   The first implementation of `_neighborhood_tables` generated the ENTIRE table space
   (`itertools.combinations(all_sources, table_size)` x `itertools.product(target_alphabet,
   repeat=table_size)`) and only filtered by Hamming distance afterward. At `table_size=8` over
   the 16-symbol EVA target alphabet that is `16**8` ~= 4.3 billion candidates generated before any
   filtering — regardless of how small the requested `radius` was. This was not caught by any
   unit-scale test (`discriminative_benchmark.py`'s cases are all `table_size<=6`); it surfaced
   only when the actual pre-registered dev grid ran a `table_size=8` cell whose deletion/
   abbreviation mode falls outside `solver_cpsat.py`'s scope (`VARIANT_SELECTIVE_DELETION`,
   `VARIANT_ABBREVIATION`, and 3 other `VARIANT_*` cells), routing it into this fallback path.
   The dev grid process ran for **4.5 hours of CPU time** before being noticed and killed — it
   would not have terminated in any practical timeframe. Fixed by constructing candidates directly
   (choose which `<=radius` of the `table_size` *existing* keys to retarget, enumerate only their
   new values: `C(table_size,r) * |target_alphabet|**r`, ~7,300 candidates at radius=2 instead of
   billions) rather than generate-then-filter. Verified fast (0.11-0.13s) on all 5 previously-hanging
   `VARIANT_*` cells after the fix, with the fixed dev grid re-run producing identical results on
   every cell the (interrupted) first run had already reached. This is the single most severe
   defect this remediation caught in its own new code — worth naming explicitly because it is
   exactly the class of resource-blindness Section 19 of the task exists to force into the open,
   and it happened despite every prior review pass (design, parity testing, discriminative
   benchmark) missing it.

5. **`generator.py`'s capacity-policy violation in synthetic ground truth (CRITICAL, found by
   external review of a *passing-looking* conclusion, not by internal testing).** The matched-
   label assignment loop's fallback (`if chosen is None: chosen = rng.choice(identity_ids)`)
   ignored `capacity_policy` entirely, assigning a "true" identity to a label even when every
   capacity-legal identity was already used for that page. At `n_identities=12` over pages with up
   to 30 occurrences, this made a large fraction of "true" correspondences infeasible for ANY
   table — including the actual true table — to jointly satisfy, manufacturing an artificial
   recall ceiling (~0.42-0.52) that had nothing to do with noise, search quality, or resource
   budget. Found only when a review disputed the first sealed-benchmark pass's conclusion (100%
   precision when certified => `RESOURCE_LIMIT`) and asked how a byte-identical recovered table
   (`exact_table_recovery=True` on 44/50 certified rows) could show only ~50% recall — the
   generator's own ground truth, not the solver, turned out to be the reason. Fixed: capacity-
   exhausted "intended matches" downgrade to genuine distractors (`realized_unmatched_rate`
   reported for transparency); `n_identities` raised to 16 to make `unmatched_rate=0` actually
   realizable under `PER_PAGE_CAPACITY_1` at the tested page sizes.
6. **`generate_hidden.py` / `sealed_harness.py` instance-scale config drift.** `generate_hidden.py`
   built its own separate `GeneratorConfig` (`n_identities=12`, default `n_occurrences=57`/
   `page_split=(30,27)`) instead of the dev grid's (`n_identities=8`, `n_occurrences=30`,
   `page_split=(16,14)`) — dev and hidden instances were silently generated at different scales,
   violating "dev and hidden differ only in seed." Fixed by extracting one shared
   `sealed_harness.build_generator_config()` both call.

All six defects were found and fixed by this package's own validation machinery or by a
methodological review of its conclusions, in every case before the affected number was allowed to
stand as final — this is the specific practice v3_design's Finding F001 (fabricated benchmark
results, no validation machinery, no review of the reasoning at all) failed to have. Defects 5-6
are the most significant of the six precisely because they were caught behind a result that
*looked* like it supported a coherent, defensible conclusion (`RESOURCE_LIMIT`) — the review that
caught them worked from "is this reasoning actually sound," not from "does this number look bad."
